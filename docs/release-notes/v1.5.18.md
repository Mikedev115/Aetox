## สลับโมเดลกลางเทิร์นได้แล้ว และรุ่นถัดไปถูกตรวจไว้ก่อนถึงคิว

**เรื่องเดิม** กดเปลี่ยนโมเดลตอนเอเจนกำลังตอบ แล้วโดนปฏิเสธ — "เอเจนกำลังทำงานอยู่
รอให้เสร็จ หรือกดหยุดก่อน" การปฏิเสธนั้นมีเหตุผลจริง (สลับกลางประโยคทำให้เทิร์นที่วิ่งอยู่
จบบนเอเจนคนละตัวกับที่มันเริ่ม) แต่มันแก้ผิดจุด: คนที่ตัดสินใจไปแล้วถูกบอกให้กลับมา
ตัดสินใจใหม่ทีหลัง ทั้งที่ห้องรอมีอยู่แล้ว — ประตูอื่นทุกบานจอดคอนฟิกไว้ที่นั่นมาตั้งแต่ §185

**รุ่นนี้** ปุ่มทั้งสี่ (โมเดล ผู้ให้บริการ ระดับความคิด รูปแบบสาย) รับคำสั่งทันที
แล้วไปลงตอนจบเทิร์น เหมือนประตูอื่นทุกบาน

- **เมนูบอกว่าอะไรรออยู่** — "รอบถัดไปจะใช้ *ชื่อโมเดล*" พร้อมปุ่มยกเลิก และชิปที่ปิดอยู่
  มีเครื่องหมายนาฬิกา ชิปยัง**ไม่เปลี่ยนชื่อ** เพราะชื่อบนชิปคือตัวที่กำลังพูดอยู่ตอนนี้
- **สองปุ่มในเทิร์นเดียวคือสองการตัดสินใจ** — คิวเก็บได้คอนฟิกเดียวและทับทั้งก้อน
  ถ้าไม่มี `dialBase` การเข้าคิวผู้ให้บริการแล้วขยับระดับความคิดจะทำให้ผู้ให้บริการ
  เด้งกลับเงียบ ๆ
- **ยกเลิกได้** — และการยกเลิกคืนความจำ "โมเดลล่าสุดของผู้ให้บริการนี้" กลับไปเป็นตัวเดิมด้วย
- **ตรวจล่วงหน้าขณะตัวเก่ายังตอบอยู่** — ยิง completion 1 โทเคนผ่านไคลเอนต์ตัวเดียวกับ
  ที่แชตใช้ ทดสอบปลายทาง คีย์ และรูปแบบสายพร้อมกัน แถวคิวบอกว่า "กำลังตรวจ" / "พร้อมแล้ว"
  / "ต่อไม่ได้" พร้อมเหตุผลของผู้ให้บริการเอง

**สองข้อที่จงใจไม่ตรวจ** และทั้งคู่มาจากของที่พังจริงภายในชั่วโมงแรก:

- **สลับที่ยังอยู่ปลายทางเดิม ไม่ยิงเลย** เจ้าของเจอเองในหน้าต่างตัวเอง — เปลี่ยนแค่ชื่อโมเดล
  บน `opencode-go` แล้ว ping ออกไปทางเดียวกับที่เทิร์นกำลังสตรีมอยู่ ping ใช้เวลาเกิน
  เดดไลน์ตัวเอง แล้วแถวคิวขึ้น "ต่อไม่ได้" เกี่ยวกับผู้ให้บริการที่เห็น ๆ ว่าทำงานอยู่
  **การตรวจที่ดังบนทางที่ปกติดี ไม่ใช่การตรวจ**
- **ping ที่หมดเวลา ไม่ตั้งคำตัดสินอะไรเลย** เดดไลน์แปลว่าคำตอบไม่มา ไม่ได้แปลว่าปลายทางตาย
- **รันไทม์ที่โหลดโมเดลลงเครื่องนี้ (Ollama, LM Studio) ไม่ถูกตรวจ** เพราะ "พิสูจน์" โมเดลถัดไป
  ที่นั่นแปลว่า *โหลดมันเข้า VRAM* ก้อนเดียวกับที่ตัวกำลังพูดอยู่นั่งอยู่ — เป็นวิธีฆ่าเทิร์น
  ที่ผู้ใช้กำลังรอ ไม่ใช่การตรวจ `runsWeightsLocally` เป็นคำเดียวที่ตอบคำถามนี้ ใช้ร่วมกับ
  แถวสถานะโหลดโมเดล ซึ่งมีอยู่เพื่อผู้ให้บริการกลุ่มที่ตัวนี้ข้ามพอดี

**ที่ยังทำไม่ได้** คำตอบที่กำลังไหลอยู่ยังเปลี่ยนโมเดลกลางประโยคไม่ได้ ด้วยเหตุผลทุกข้อ
ที่ §185 วัดไว้ · การตรวจพิสูจน์ว่า *ต่อติด* ไม่ใช่ว่า *รับไหว* — ปลายทางที่ตอบ ping
1 โทเคนแล้วปฏิเสธคำขอจริงด้วยเรื่องโควตาหรือคอนเท็กซ์ ยังไปเจอตอนถึงคิวอยู่ดี ·
และคิวที่ตรวจไม่ผ่าน **ไม่ถูกห้ามลง** — รายงานให้เห็น แล้วให้ผู้ใช้ตัดสิน เพราะ
"ปลายทางนี้ล่มเมื่อ 40 วินาทีก่อน" ไม่ใช่ข้อเท็จจริงเดียวกับ "ปลายทางนี้ล่ม"

บันทึกเต็มอยู่ที่ [DECISIONS.md](../DECISIONS.md) §232 · เทสต์ที่เพิ่มในรุ่นนี้:
`desktop/turn_guard_test.go` (ปุ่มกลางเทิร์นถูกรับ, เครื่องยนต์ไม่ขยับ, คิวโผล่ใน
`ModelInfo.Pending`, ลงตอน `endTurn`, ปุ่มที่สองต่อยอดจากปุ่มแรก, ยกเลิกแล้วเครื่องยนต์อยู่ที่เดิม,
คิวที่ไม่ขยับปุ่มไหนเลยไม่วาดอะไร, คิวที่เปลี่ยนแค่ชื่อโมเดลไม่ถูก ping, คิวรันไทม์ในเครื่อง
ไม่ถูก ping) และ `desktop/frontend/src/test/modelQueue.test.ts`

## บันทึกที่เปิดย้อนหลังแล้วยังครบ

สามเรื่องที่ไม่เกี่ยวกัน แต่เป็นอาการเดียวกัน: **สิ่งที่เกิดขึ้นตอนเทิร์นวิ่ง หายไปหมด
เมื่อเปิดเซสชันกลับมา**

### ลูกน้องทำอะไรไปบ้าง

**เรื่องเดิม** แถวเครื่องมือของซับเอเจนเป็นการถ่ายทอดสด — หน้าต่างวาดมัน ไม่มีใครเก็บ
เปิดแชตเก่ากลับมา การ์ดมอบหมายบอกได้แค่ว่ามีคนถูกจ้าง ไม่บอกว่าเขาทำอะไร

**รุ่นนี้** ลำดับ `TurnPart` ของลูกน้องถูกเก็บไว้ใต้ ref ของคอล `task` ที่จ้างมัน
(`OnChildParts` → `recordChildParts` → `withChildParts`) เป็นบันทึกชุดเดียวกับที่พ่องาน
เก็บให้ตัวเอง ส่งมอบไม่ว่าจะจบยังไง — ลูกน้องที่ตายกลางทางก็ทำงานไปถึงกำแพงแล้ว
และครึ่งนั้นคือส่วนที่คนเปิดการ์ดกลับมาอ่านจริง ๆ

### ถามอะไร แล้วเราตอบอะไร

**เรื่องเดิม** การ์ดคำถามถูกวาดอยู่ในเทิร์นสด และหายไปทันทีที่ตอบ เปิดเซสชันวันถัดมา
เหลือแถวที่บอกว่า "ถามคุณ" โดยไม่มีทั้งคำถามและคำตอบอยู่บนนั้น (เจ้าของ 7 ก.ย.:
*"ควรจะดูย้อนหลังได้ว่า ถามอะไรและเราตอบอะไร"*)

**รุ่นนี้** `skill.Output.Answer` → `ToolEvent.Answer` → `ToolPart.Answer` เขียนลงจริง
เป็นฟิลด์ JSON ใหม่ในคอลัมน์ `parts` เดิม จึงไม่ต้อง migration แถวเก่าก็แค่ไม่มีมัน
บนแถว คำตอบกินความกว้างก่อนและคำถามถูกตัดข้างหลัง ซึ่งกลับด้านกับทุกแถวในลิสต์ —
และถูกสำหรับแถวเดียวที่หัวเรื่องเป็นประโยค เพราะคำถามเดาจากงานรอบข้างได้ คำตอบเดาไม่ได้
`question` ยังเข้าไปอยู่ใน `ArgSubjectKeys` ด้วย แถวจึงมีคำถามตั้งแต่ตอนที่ JSON ยังไหลไม่จบ

### แถวรอผลงาน ไม่แย่งที่การ์ดอีกแล้ว

**เรื่องเดิม** คอล `task collect` เป็นแถวไร้ชื่อว่า "รอผลงาน · 13s" นั่งอยู่เหนือการ์ด
ของลูกน้องที่สิบสามวินาทีนั้นเป็นของเขา — ตัวเลขอยู่ผิดวัตถุ ส่วนการ์ดเองไม่มีนาฬิกาเลย
เมื่อทะเบียนถูกล้าง และมันยังดันเลข "ใช้ N เครื่องมือ" ขึ้นหนึ่ง

**รุ่นนี้** `collectedTask` อ่าน id ของงานออกจากอาร์กิวเมนต์ของ `collect` (และ `answer`)
มาแปะบนแถว ตอนกำลังรอ แถวยังอยู่ — เอเจนถูกบล็อกอยู่จริง และ "รอผลงาน · 8s" คือสิ่งเดียว
บนจอที่พูดแบบนั้น พอผลกลับมาแถวหายไปและวินาทีของมันไปขึ้นบนการ์ดของลูกน้องแทน
จงใจไม่แปะกับ `start` เพราะ start ยัง**ไม่มี** id (ทะเบียนเป็นคนออกให้ในผลลัพธ์) และหลาย id
คั่นจุลภาคก็ปล่อยว่าง ดีกว่าเลือกอันแรกมาอ้างว่าแถวนี้เกี่ยวกับตัวไหน

เทสต์ที่เพิ่มในรุ่นนี้: `internal/turn/collected_task_test.go`, `desktop/ask_user_test.go`,
`internal/model/partialargs_test.go`, `desktop/frontend/src/test/askRowRecord.test.ts`,
`desktop/frontend/src/test/subagentCard.test.ts`

## แถวเครื่องมือพับเก็บอย่างสุภาพ และคำตอบไม่มีแสงวิบวับแล้ว

**เรื่องเดิม** เจ้าของพูดเรื่องนี้สามครั้งในวันเดียว เพราะสองคำตอบแรกผิดคนละแบบ:
*"ตอนมันรัน tool เสร็จ มันควรจะพับเก็บอย่างสุภาพ แบบค่อยๆ ดุนุ่มๆ ... ตอนนี้มันแบบ พึ๊บไปเลย"*

กติกาที่ลองมาแล้วสี่ข้อ แต่ละข้อแก้ข้อก่อนหน้าจริง และแต่ละข้อซื้อคำบ่นใหม่มา:

1. **พับสิ่งที่เสร็จแล้ว ทีละแถว** — พับคอลทิ้งในเฟรมที่ผลลัพธ์ลง สกิลที่ตอบในครึ่งวินาที
   อยู่บนจอเฟรมเดียว และลูกน้องที่เพิ่งกลับมาพาการ์ดตัวเองหายไปด้วย
2. **ไม่พับอะไรเลยจนจบเทิร์น** — ถือประวัติทั้งเทิร์นเปิดไว้ แล้วทำให้ตอนจบเป็นการหายไป
   ทีเดียวก้อนใหญ่ คือ "พึ๊บ" นั่นเอง
3. **พับตอนประโยคถัดไปมาถึง** — ขอบเขตถูก แต่ช้าไปหนึ่งรอบ โมเดลคิดเป็นนาทีระหว่าง
   ผลลัพธ์สุดท้ายกับคำถัดไปได้ และแถวที่เสร็จแล้วนั่งอยู่อย่างนั้นตลอด
4. **พับตอนช่วงงานเงียบลง** — ตอนคอลสุดท้ายใต้ประโยคนี้กลับมา ซึ่งคือสิ่งที่เขาอธิบาย
   มาตั้งแต่ต้น

**รุ่นนี้** `working` เป็นคำถามเดียวที่บล็อกช่วงงานถาม — มีคอลค้างอยู่ไหม ถ้ามี
ทั้งลิสต์อยู่บนจอในหน้าต่างที่เลื่อนได้ (`toolWindow.ts` แบบเดียวกับช่องความคิด)
หัวข้อข้างบนเป็น**เส้น ไม่ใช่ปุ่ม** เพราะลิสต์ที่มีอะไรขยับอยู่ต้องไม่อยู่ห่างจากการถูกซ่อน
แค่คลิกเดียว พอไม่มีอะไรค้าง หัวข้อกลายเป็นปุ่มและลิสต์พับเข้าไปในนั้น

- **`settle` เป็นทรานซิชันตัวที่สองข้าง `fold`** — ยาวสองเท่า (520ms), `cubicInOut`
  เพราะ `cubicOut` บนขา**ออก**คือค้างแล้วร่วง, และความทึบลดลงพร้อมความสูง เพราะการตัด
  ก็ยังเป็นการตัดต่อให้ใช้เวลานานแค่ไหน มันยังยกเลิกช่องไฟ 8px ของ `.phase` ด้วย
  ซึ่งพาเรนต์แบบ flex ถือไว้ทั้งก้อนจนถึงเฟรมที่ลูกถูกถอด — พิกเซลสุดท้ายของการพับ
  ที่นุ่มที่สุดเลยเป็นการกระตุก
- **การพับรับสถานะที่ถูกส่งมา** เพราะแถวที่เข้าไปในฟold กับที่ออกมาถูกวาดด้วย
  *อีลิเมนต์คนละตัว* — สองรอบ ทั้งตอน working→quiet และตอนสด→บันทึก
- **การ์ดมอบหมายไม่พับ ไม่ว่าจังหวะไหน** กำลังทำงานหรือเสร็จแล้ว แถวเครื่องมือคือใบเสร็จ
  ที่พับเป็นตัวเลขได้ ส่วนการ์ดมอบหมายคืองานของคนอื่นที่มีหน้าอยู่บนนั้น และ
  "ซับเอเจน 1 ตัว" แทนกันไม่ได้

**และแสงวิบวับออกจากคอลัมน์คำตอบแล้ว** เจ้าของสั่งเรื่องนี้กับการ์ดมอบหมายไปเมื่อเดือนก่อน
แล้ววันที่ 7 ก.ย. สั่งอีกขั้น — เอาออกจากบทสนทนาทั้งหมด ข้อสังเกตเดิมของ §112.1
ยังถูกและไม่ได้ถูกถอน (แผน ภาพวาด และโค้ดยาว *อ่านเหมือนเสร็จแล้ว* ตั้งแต่เฟรมแรก)
สิ่งที่ถอนคือคำตอบ: ลำแสงถูกยืมมาจากการ์ดในลิสต์ทรงไซด์บาร์ แล้วเอามาใส่คอลัมน์เดียว
ในแอปที่เป็น **ร้อยแก้ว** — ที่นั่นมันไม่ได้แข่งกับกรอบ มันแข่งกับประโยคที่กำลังถูกอ่าน
สิ่งที่บอกว่า "ยังไม่หมด" ตอนนี้คือ**ประโยครอ**ใต้ข้อความ ซึ่งอยู่บนจอนานเท่าที่ยังมีอะไรมา
พูดเป็นคำ และนั่งอยู่ใต้การอ่านแทนที่จะล้อมรอบมัน

บันทึกเต็ม §233 และ §112.4 · เทสต์: `Chat.tools.test.ts`, `fold.test.ts`,
`beam.test.ts`, `drawing.test.ts`

migrate ไปถึงสคีมา 18 แล้ว ทุกลิสต์ในแอปกลับมาว่าง — 77 เซสชันยังอยู่บนดิสก์
ไม่มีสักอันบนจอ และ**ไม่มีสักบรรทัดในล็อกที่บอกว่าทำไม** ผู้เรียกกลืน error แล้วคืนสไลซ์ว่าง
ส่วนการล็อกของ `eachRow` ไม่เคยทำงานเพราะไม่มีคิวรีไหนไปถึง — แอปจึงเงียบสนิท
ในกรณีที่มันมีเรื่องจะพูดมากที่สุด

**รุ่นนี้**

- **ความล้มเหลวถูกล็อก** ไม่เคยมีอะไรล็อกมันมาก่อน
- **ความล้มเหลวไม่จำเป็นต้องถูกจำ** `sync.Once` ทำให้ error แรกเป็นคำตอบไปตลอดอายุ
  โปรเซส ดิสก์ที่ไม่ว่างแค่วินาทีเดียว (อีกอินสแตนซ์กำลังเขียนปิดตัว) เลยทำให้หน้าต่างนั้น
  ไม่มีประวัติจนกว่าจะรีสตาร์ต ตอนนี้มีแต่ `schemaTooNewError` ที่ถาวร ที่เหลือลองใหม่
  อย่างมากทุก 3 วินาที
- **ไซด์บาร์แยกสองประโยคออกจากกัน** "ยังไม่มีแชต" กับ "อ่านแชตไม่ได้" ไม่ใช่ประโยคเดียวกัน
  และคอลัมน์นี้วาดอันแรกให้ทั้งสองกรณีมาตลอดอายุของลิสต์ กรณีไฟล์ใหม่กว่าบอกเลขสคีมาทั้งสองตัว
  และบอกว่าแชตเก่ายังอยู่ครบ
- **แบนเนอร์หายไปเอง** `HistoryFault` ถาม `database()` ใหม่แทนที่จะอ่าน error ที่แคชไว้
  สโตร์ที่กลับมาได้แล้วรายงานว่าไม่มีปัญหา — ตัวหน่วงลองใหม่ข้างบนคือสิ่งที่กันไม่ให้
  การถามแบบนั้นเสียค่าเปิดไฟล์หนึ่งครั้งต่อการรีเฟรช

เทสต์: `desktop/db_test.go`, `desktop/frontend/src/test/sidebarHistory.test.ts`

## batch ของเบราว์เซอร์หยุดเมื่อหน้าเปลี่ยนใต้เท้า

**เรื่องเดิม** เจ้าของถามเช้าวันถัดจากที่ `steps` ลง: *"มันทำงานแบบ 1 call ต่อ 1 แอ็คชั่น
มันมีวิธีที่ดีกว่านี้ไหมครับ"* — ถามถึง batch ที่เพิ่งปล่อยไปเมื่อคืน นั่นคือ**การค้นพบ**
ไม่ใช่การจำผิด: คำแนะนำเรื่องการรวบคอลถูกผูกไว้กับ `steps` เอง และคำแนะนำที่ผูกกับแอ็คชัน
จะมาถึงตอนใช้แอ็คชันนั้นครั้งแรก — คำแนะนำเรื่องการ batch จึงไปถึงเฉพาะโมเดลที่ batch เป็นอยู่แล้ว

**รุ่นนี้** สองส่วน

- **batch หยุดเมื่อหน้าเลื่อนออกจากใต้ขั้นที่มองไม่เห็นว่ามันเลื่อน** การเล็งที่ค้างอยู่
  ไม่ *ล้มเหลว* ซึ่งคือสิ่งที่ทำให้มันแย่กว่าความล้มเหลว: ref 3 บนหน้าที่เพิ่งมาถึงเป็น
  อีลิเมนต์จริง และ x,y จากภาพเก่าเป็นตำแหน่งจริงบนจอ คลิกจึงลง รายงานว่าสำเร็จ
  แล้ว batch เดินหน้าทำสิ่งที่ไม่มีใครสั่งต่อไป `open` กับ `tabs select` เป็นการนำทาง
  โดยนิยาม รู้ได้โดยไม่ต้องถาม ที่เหลือจับด้วยการเทียบ URL ที่ settle จ่ายไปแล้ว
  `find` เป็นข้อยกเว้นและไปต่อ เพราะมันหาบนหน้าที่มันลงจอด และปฏิเสธแทนที่จะเดา
- **batch ถูกสอนโดย `open` และ `click`** ประโยคละหนึ่งบรรทัด ตรงที่ทุกเซสชันเบราว์เซอร์
  ผ่านอยู่แล้ว

**ที่ยังทำไม่ได้** จับหน้าที่เปลี่ยนโดยไม่เปลี่ยน URL ไม่ได้ — โมดัล การเรนเดอร์ใหม่
ฟีดที่ไหลไม่จบ สัญญาณที่ใช้คือสัญญาณที่ change note จ่ายอยู่แล้ว ตัวนับ DOM mutation
คือขั้นถัดไปและยังไม่มีใครต้องการมัน

บันทึกเต็ม §231 · เทสต์: `desktop/browser_steps_test.go`

## เตรียมคำตอบไว้ให้ในช่องพิมพ์

**เรื่องเดิม** เทิร์นที่จบด้วยการยื่นทางแยกให้ — "ทำ a หรือ b" — จบลงโดยที่ข้อความถัดไป
ของผู้ใช้ถูกตัดสินใจไปแล้วทุกอย่าง เหลือแค่การพิมพ์

**รุ่นนี้** คำนั้นถูกเขียนลงช่องพิมพ์เป็นตัวจางก่อนมือจะถึงคีย์บอร์ด Tab รับไปใช้
Tab อีกครั้งสลับไปคำของอีกตัวเลือก พิมพ์อะไรก็หายไป **ไม่มีอะไรถูกส่ง** และไม่มีอะไร
ถูกใส่ในกล่องที่ไม่ได้มาจากการกดปุ่ม

สองกติกาที่ตัดสินว่าเมื่อไหร่มันได้รับอนุญาตให้เสียเงิน มาจากเจ้าของทั้งคู่
(*"มันไม่ควรเป็นช้อยบังคับ… บางงานมันไม่จำเป็นต้องสร้างคำตอบรอ"*):

1. `offersChoice` อ่านคำตอบที่เขียนจบแล้วโดยไม่ใช้โมเดลเลย เทิร์นที่จบด้วย
   "แก้ไฟล์ให้แล้ว เทสต์ผ่าน" ไม่เหลืออะไรให้ตัดสินใจ จึงไม่มีคอลไหนถูกยิง —
   ไม่ใช่ยิงแล้วทิ้ง แต่ไม่ยิงเลย
2. ที่รอดกติกาข้อแรกเสียคอลเล็ก ๆ **หนึ่งคอล** หลังคำตอบขึ้นจอแล้ว นอกเส้นวิกฤติของเทิร์น

**ทำไมเป็นคอลที่สอง ไม่ใช่เครื่องมือที่โมเดลเรียกเอง** ทรงนั้นคือ `suggest_task` เป๊ะ ๆ
ซึ่งถูกตัดทิ้งเมื่อ 29 ส.ค. หลังจากบล็อกเครื่องมือ 270 โทเคนในทุกคำขอบนทุกโต๊ะ
ซื้อการเรียกได้ **ศูนย์ครั้งใน 6,253 รอบ** เครื่องมือคือภาษีประจำที่เก็บจากทุกคำขอ
โดยหวังว่าโมเดลจะหยิบ ส่วนนี่คือค่าใช้จ่ายบนเทิร์นที่จบด้วยคำถามจริง ๆ ตัดสินโดยฟังก์ชัน
ที่อ่านได้และเทสต์ได้ ปิดได้จากหน้าตั้งค่า (มาแบบเปิด)

เทสต์: `desktop/prepared_reply_test.go`, `desktop/frontend/src/test/preparedReply.test.ts`

## ทั้งแอปเคลื่อนไหวด้วยคำศัพท์ชุดเดียว

**เรื่องเดิม** ชั้นโทเคนการเคลื่อนไหวมีอยู่แล้วใน `styles/type.css` (`--dur-press`,
`--dur-arrive`, `--dur-settle`, `--beam-*`, `--swap-*`, `--ease-arrive`) พร้อม
`lib/motion.ts` ที่อ่านค่าจากโทเคนแทนการเขียนเลขซ้ำใน TypeScript — **และแอปเดินผ่านมันไป**
นับใน `style.css` วันที่ 7 ก.ย.: `transition:` 54 จุด ถือความยาว **28 ค่าไม่ซ้ำ**
โดยมีแค่หน้าเปิดโปรแกรมครั้งแรกกับแถวเครื่องมือที่ใช้โทเคนจริง

รูปร่างของกองนั้นไม่ใช่ความไม่ลงรอย — มันคืองานสองอย่างที่ถูกเขียนด้วยมือซ้ำแล้วซ้ำอีก:
สี่สิบจุดเปลี่ยน**สี**ตอนเมาส์มาถึง (`.12s` 44 ครั้ง, `.15s` 17 ครั้ง, 140ms หลงมาหนึ่ง)
ที่เหลือขยับ**ความยาว** (`.18s`, `.2s`, `.22s`)

**รุ่นนี้** สองชื่อ ค่าเป็นค่าที่แอปโหวตให้เองอยู่แล้ว ไม่ใช่ความเห็นใหม่:
`--dur-tint:120ms` (สีตอบเมาส์: hover, focus, เปิด/ปิด) และ `--dur-glide:180ms`
(ความยาวที่เปลี่ยน: แผงกว้างขึ้น แถบเติม) แล้วกวาดทั้งไฟล์ให้ไปใช้มัน

- **เมนูลอยทั้งสิบตัวมีจังหวะตอนเปิดแล้ว** มันเป็นพื้นผิวเดียวกันที่ถูกเขียนสิบครั้ง
  (absolute, `--surface-panel`, เส้น `--border-subtle`, `--shadow-menu`) และไม่มีสักตัว
  ที่มี**การมาถึง** — ทุกตัวปรากฏเต็มรูปในเฟรมเดียว ซึ่งเป็นสิ่งเดียวที่ชั้นลอยเหนือหน้า
  ไม่ควรทำ เพราะไม่มีอะไรบนจอบอกว่ามันมาจากไหน ตอนนี้มันงอกออกจากขอบที่มันเกาะอยู่
  ด้วย `--dur-tint` ตัวเดียวกับที่ปุ่มตอบเมาส์ — การเปิดเมนูคือการกด ไม่ใช่การเปลี่ยนหน้าจอ
- **มีด่านกันไม่ให้เดินผ่านมันอีก** `motionTokens.test.ts` ล้มเมื่อมี `transition:`
  ที่เขียนความยาวเป็นตัวเลขดิบ (ดีเลย์ยังเป็นตัวเลขได้ — มันไม่ใช่ความยาวของการเคลื่อนไหว)
  และล้มเมื่อมีเมนูหลุดจากรายชื่อการมาถึง

## อื่น ๆ ในรุ่นนี้

- **หน้าเอเจนมีสีหน้าจริงแล้ว** `agentFace.ts` วาด `think` / `work` / `done` / `err`
  มาตั้งแต่หน้าพวกนี้ลง — แล้วไม่มีผู้เรียกไหนส่ง `state` เลยสักตัว ทุกหน้าในแอปจึงเป็น
  หน้านิ่งมาตลอด รุ่นนี้ต่อสายให้การ์ดถาดงานและการ์ดมอบหมายในแชต โดย `think` กับ `work`
  แยกกันด้วยว่ามีแถวลูกกำลังรันอยู่ไหม
- **บรีฟถูกเขียนออกมาตอนส่งมอบ** (`typeOnce.ts`) การ์ดมาถึงทันทีเพราะการ์ดโผล่ =
  โมเดลเริ่มมอบหมายจริง แต่บรีฟตามมาอีกจังหวะ เพราะมันคือสองเหตุการณ์ ไม่ใช่หนึ่ง:
  มีคนถูกจ้าง แล้วเขาถึงถูกบอกว่าให้ทำอะไร มันไม่ใช่ `pacedText` และไฟล์นั้นอธิบายว่าทำไม —
  บรีฟไม่ได้สตรีม มันมีครบตั้งแต่วินาทีที่มอบหมายเริ่ม การ์ดที่อ่านกลับจากฐานข้อมูล
  ได้บรีฟทันที เพราะไม่มีอะไรกำลังถูกส่งมอบให้ใคร
- **ลิสต์ของลูกน้องมีเพดานเหมือนของเอเจนเอง** ลูกน้องเป็นตัวเดียวที่รันได้ยี่สิบนาที
  ลิสต์ของมันจึงเป็นลิสต์ที่ยาวที่สุดและเป็นตัวเดียวที่ยังโตไม่หยุด ใช้ `state === 'run'`
  ไม่ใช่ `live` เพราะการมอบหมายอยู่ข้ามเทิร์นที่เริ่มมันได้
- **แถวเซิร์ฟเวอร์ MCP ของเอเจนมีโลโก้และสวิตช์ของแอป** หน้าตั้งค่า › MCP ให้เซิร์ฟเวอร์
  ห้าตัวเดียวกันนี้มีโลโก้อยู่แล้ว ส่วนกล่องนี้ให้ข้อความเทาห้าบรรทัดที่หน้าตาเหมือนกันหมด —
  ทั้งที่นี่คือหน้าที่ต้องเลือกหนึ่งในห้า และเช็คบ็อกซ์ดิบตัวสุดท้ายในหน้านั้นก็กลายเป็น
  `.mswitch` เหมือนสวิตช์อื่นทุกตัว
- **`oneShotProviderFor`** งานที่ตามหลังเทิร์นที่จบแล้วต้องระบุแชตมาตรง ๆ ไม่ใช่อ่าน
  `a.cur()` ย้อนหลัง — เทิร์นที่จบตอนผู้ใช้กำลังอ่านแชตอื่นจะถูกตามด้วยโมเดลของแชตนั้นแทน
