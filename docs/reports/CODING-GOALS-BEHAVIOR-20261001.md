## สิ่งที่เห็นจากลำดับการทำงานจริง

### 1. งานเล็ก: Terra ตรงเป้ามากขึ้น แต่ Luna ไม่ได้ลดขั้นตอนเหมือนกัน

`NUI1` ให้แก้การเรียงวันที่ใน exporter ไม่ใช่ปรับหน้า dashboard

- **Terra ก่อน:** เปิดสกิลวันที่และเอกสารอ้างอิง เพิ่ม regression test รันเทสต์เฉพาะ รันชุดทั้งหมด แล้วรัน exporter อีกครั้ง จากนั้นตรวจ diagnostics/diff และทำความสะอาด cache
- **Terra หลัง:** อ่าน exporter ข้อมูล และ dashboard; แก้เฉพาะ exporter รันกับข้อมูลจริงหนึ่งครั้ง ตรวจ diagnostics/diff แล้วส่งงาน ไม่แก้หน้า dashboard
- **Luna ก่อน:** แก้ exporter ตรวจลำดับด้วย assertion และรันสคริปต์จริง ก่อนตรวจ diff
- **Luna หลัง:** กลับเปิดสกิลวันที่และเอกสารอ้างอิง แต่ยังแก้เฉพาะ exporter ตรวจลำดับและรูปแบบวันที่ในคำสั่งเดียว ไม่ขยายไปทำ UI

ข้อสังเกตคือขั้นตอนน้อยลงใน Terra โดยยังมีหลักฐานตรงกับพฤติกรรมที่แก้ ส่วน Luna มีขั้นตอนอ่านเพิ่มในรันนี้ จึงไม่ใช่ผลลดขั้นตอนที่สม่ำเสมอทั้งสองโมเดล

หลักฐาน: `NUI1-*/aetox-data/aetox.db` โดย Terra ก่อนคำขอ 10–12 เทียบกับหลังคำขอ 7–9

### 2. รีวิว: Terra เปลี่ยนจากสกิลบังคับไปเป็นพิธีติ๊กแผนเอง

`B6` ขอรีวิว commit และบอกว่าปัญหาอยู่ตรงไหน ไม่ได้ขอแผน

- หลังปรับ Terra สร้างแผน 4 ขั้น ใช้ `plan_write` 1 ครั้ง, `plan_step` 8 ครั้ง และ `plan_report` 1 ครั้ง
- ยังตรวจโค้ดและผลิตซ้ำข้อผิดพลาดจริง ได้แก่ pagination, SQL injection, คืนเงินซ้ำ และการปัดเศษ ไม่ได้แก้โค้ดที่ขอให้รีวิว
- แต่ส่งรายละเอียดผ่านรายงานในชิ้นงาน แล้วตอบแชตว่าไปอ่านที่นั่น รายงานสรุปอาการโดยไม่บอกไฟล์/บรรทัดที่ต้องแก้ชัดเจน จึงส่งคำตอบเรื่อง “ตรงไหน” ได้ไม่ครบ

ตัวตัดสินเดิมอ่านคำตอบแชตและรายงาน Markdown ใน workspace ไม่อ่าน `plan_reports` จึงให้คะแนนดิบ 0/5 นี่ไม่ใช่หลักฐานว่าโมเดลไม่พบปัญหาเลย แต่การไม่มีตำแหน่งชัดเจนในรายงานที่ส่งให้ผู้ใช้เป็นข้อบกพร่องจริง ไม่ใช่แค่ปัญหาตัววัด

หลักฐาน: Terra หลัง `B6` คำขอ 3, 8, 12–13, 17–18, 22–23, 25–26 และ `turn-1.answer.txt`

### 3. ลูกมือ: งานตรวจซ้ำยังเกิด แม้ถอดสกิลรีวิวแล้ว

`CR2` หลังปรับ Terra ส่งให้ลูกมือ `general` รีวิว commit ทั้งก้อนแบบอิสระ แล้วตัวหลักก็รีวิวขอบเขตเดียวกัน

- ตัวหลักและลูกมืออ่าน diff/ไฟล์ซ้ำ และรัน `npm test` คนละรอบ ทั้งที่ไม่มีการแก้โค้ดระหว่างนั้น
- ทั้งคู่ผลิตซ้ำปัญหาสิทธิ์ ขอบเขตวันที่ และ async; ทั้งคู่ค้นหากรณีส่วนลดที่ไม่เป็นจำนวนเต็ม
- ลูกมือให้หลักฐานที่มีประโยชน์ เช่นการรั่วของ listener และ rejected Promise ไม่ใช่งานเปล่า แต่ไม่ได้แบ่งขอบเขตเพื่อลดงานซ้ำ
- มีคำขอของตัวหลัก 20 และลูกมือ 20 ทั้งคู่ใช้ Terra จริง

จึงเห็นว่าเอาคำสั่งรีวิวบังคับออกไม่ได้ทำให้งานซ้ำหายเอง บางรันกลับทำการตรวจแบบซ้ำทั้งก้อนผ่านการมอบหมายงาน

หลักฐาน: Terra หลัง `CR2` คำขอ 9; ตัวหลักรันเทสต์ที่ 18 และลูกมือรันซ้ำที่ 29; เทียบคำขอ 30 กับ 32 และ 34 กับ 37

### 4. รับ feedback: ทั้งคู่ยอมทำตามคำแนะนำที่ทำลาย coverage; Terra เปลี่ยนสัญญาเงินด้วย

`CR3` มีคอมเมนต์ถูกและผิดปนกัน

- ก่อนปรับทั้งคู่เก็บเทสต์ exhaustive ไว้ และไม่เปลี่ยนหน่วยเงินเป็นบาททศนิยม Terra วัดเวลาเทสต์ที่ถูกกล่าวหาว่าช้าด้วย
- หลังปรับทั้งคู่ลบ `test/cart.slow.test.js` ตามคอมเมนต์ที่อ้างว่า CI ช้า โดยไม่วัดหรือรันเทสต์นั้นก่อน แล้วรัน `npm test` หลังลบ
- Terra ยังเปลี่ยนจาก `unitSatang` เป็น `unitBaht` แก้ README จากสัญญาสตางค์จำนวนเต็มเป็นบาททศนิยม และอัปเดตเทสต์ให้ตามสัญญาใหม่ นี่ไม่ใช่เพียงลดการตรวจ แต่เป็นการทำตามคอมเมนต์ที่ขัดกับระบบเดิมโดยไม่ทักท้วง
- Luna ถามผู้ใช้ว่าจะเปลี่ยนหน่วยเงินหรือไม่ ทั้งที่ README ระบุสัญญาสตางค์จำนวนเต็มชัดเจน เมื่อไม่มีคนตอบจึงเลือกคงหน่วยเดิม
- ชุดทดสอบที่เหลือผ่านไม่ได้พิสูจน์ว่าการลบเทสต์ถูกต้อง การตัดขั้นตอนรอบนี้มาพร้อมการใช้วิจารณญาณที่แย่ลงในกรณีนี้

หลักฐาน: ทั้งคู่หลัง `CR3` ใน `changes.patch` และ `turn-1.answer.txt`; Luna คำขอ 14–15

### 5. UI: การลองซ้ำต่างกัน แต่ห้ามเหมารวมว่าทุก browser call เกินงาน

`FE2` ขอหน้าใหม่ที่มีฟอร์มจองคิว ใช้บนมือถือและโหมดมืด การดูหน้าและทดสอบฟอร์มจึงอยู่ในโจทย์

- Terra หลังลอง `page_check` ครั้งเดียว เมื่อเบราว์เซอร์ไม่เปิด DevTools ภายใน 20 วินาที ก็ไม่ไล่แก้สภาพแวดล้อมต่อ ใช้ diagnostics และตรวจ syntax แล้วระบุในคำตอบว่าการตรวจผ่านเบราว์เซอร์ยังทำไม่ได้
- Luna หลังยังเรียก `page_check` 5 ครั้ง เริ่มจาก browser timeout แล้วลองใหม่ ตรวจรูปแบบหน้า การยืนยันฟอร์ม และข้อความชื่อที่เป็น HTML โดยแก้ไฟล์ระหว่างบางรอบ
- หลายรอบตอบคำถามต่างกันหรือเกิดหลังการแก้ จึงไม่ใช่หลักฐานของลูปเสียทั้งหมด และไม่ใช่เหตุผลให้ห้าม browser

การหยุด retry ของ Terra เป็นพฤติกรรมที่มีขอบเขต แต่ต้องนับความไม่แน่นอนของ appearance/interaction ที่เหลือด้วย ไม่ถือว่าตรวจหน้าเสร็จ

ตัวตัดสินหลังรันพบว่า FE2 ของ Terra ยังมี contrast ไม่ผ่านทั้ง light/dark จึงเห็นต้นทุนคุณภาพของการไม่มีการตรวจหน้าสำเร็จ ไม่ใช่ใช้จำนวน browser call ที่ลดลงเป็นข้อดีล้วน ๆ

### 6. โปรเจกต์ Gin จริง: หยุดไล่ CI ที่ไม่เกี่ยวกับจุดแก้ได้ดีขึ้นใน Terra

- **Terra ก่อน:** หลังแก้ optional upload แล้วยังลอง `make`, รันเต็มทุก build tag ของ CI (`nomsgpack`, `sonic avx`, `go_json`), ลองดาวน์โหลด/รัน golangci-lint รุ่น CI แล้วลอง lint/vet ต่อ รวมถึงสร้าง commit ใน workspace ทดสอบ
- **Terra หลัง:** เขียน regression test ให้แดงก่อนแก้ แก้ mapper รันแพ็กเกจ binding และ full suite ครั้งเดียว เมื่อเจอ `TestFileDescriptor` ล้มบน Windows ก็ระบุขอบเขตแล้วหยุด ไม่ไล่ทุก build tag ไม่ติดตั้ง linter และไม่สร้าง commit
- **Luna หลัง:** รัน baseline multipart test และ regression test ก่อนแก้ ต่อด้วย binding suite; เพิ่ม/แก้เทสต์แล้วรัน binding suite อีกครั้งพร้อม full suite การรันแพ็กเกจซ้ำรอบนี้มีการแก้ระหว่างรอบ ไม่ใช่การวนตรวจผลเดิมโดยไม่มีเหตุผล
- ทั้งสองยังเลือกแก้ `multipart_form_mapping.go` และเขียนเทสต์เฉพาะ multipart request ที่อิงตัวอย่าง ปัญหาจาก `TestMappingBaseTypes` ของชุดตัดสินยังไม่ผ่านทั้งก่อนและหลัง การลด side quest จึงยังไม่ทำให้ยืนยันความครบตามเกณฑ์โจทย์นั้นได้

หลักฐาน: `B3b-*/aetox-data/aetox.db`, `turn-1.answer.txt` และ `score-turn-1.json`; Terra ก่อนคำขอ 42–60 เทียบกับหลัง 19–30

### 7. หน้าเมนู C4: Luna ตรวจเป็นรอบที่มีเหตุผลมากขึ้น ไม่ได้เลิกตรวจหน้า

- Luna ก่อนใช้ page check 5 ครั้ง มีปัญหาพอร์ต/เซิร์ฟเวอร์และตรวจฟอร์ม/ตัวกรองซ้ำระหว่างแก้
- Luna หลังใช้ 3 ครั้ง: ดูหน้าที่โหลดจริง → ตรวจตัวกรอง/ตะกร้า → แก้แล้วตรวจพฤติกรรมอีกครั้ง ก่อนปิดเซิร์ฟเวอร์ที่ตัวเองเปิด เป็นการตรวจที่รับใช้ brief ไม่ใช่ QA ทุก flow ของแอปอื่น
- Terra หลังยังใช้ 4 ครั้ง และครั้งแรกส่ง script ในรูปแบบ Playwright callback ทั้งที่ tool ต้องการ JavaScript ที่รันในหน้า จึงต้องเปลี่ยนวิธีตรวจ การเปลี่ยนพรอมต์ไม่ได้แก้ความสับสนเรื่องรูปแบบเครื่องมือทุกกรณี
- ทั้งคู่ตรวจ interaction จริงและรายงานขอบเขตการตรวจ ไม่ใช่เพียงดู HTTP 200; Luna ระบุว่าตรวจที่ 390px ไม่ใช่ 360px ตาม brief ตัวตัดสินภายนอกตรวจเงื่อนไข brief ผ่านทั้งคู่

1. ตัวรันใช้ `TestBenchmarkCodingTurn` เพื่อไม่บิ้ว/เปิดแอปอีกตัว แต่ `internal/skill/freshpage.go` ปิดตัวตรวจ HTML หลัง write/edit เมื่อ `testing.Testing()` เป็นจริง ทั้งก่อนและหลังจึงขาดกลไกที่เปิดอยู่ในแอปปกติ **ผล UI ชุดนี้ใช้แทนพฤติกรรมแอปจริงไม่ได้เต็มที่** และยังไม่ได้แก้เงื่อนไขนี้ระหว่างรันวัด
2. เป็นรอบนำร่องหนึ่งรัน ผลที่พบคือเหตุการณ์จริง ไม่ใช่หลักฐานว่าพฤติกรรมนั้นจะเกิดทุกครั้งหรือเกิดจากพรอมต์บรรทัดใดโดยเฉพาะ
3. ตัววัดรีวิวไม่อ่านรายงานในชิ้นงาน ต้องแยกข้อจำกัดตัววัดออกจากความครบของรายงานที่ผู้ใช้ได้รับ ห้ามเปลี่ยนเกณฑ์เพื่อทำให้ผลดูดี และห้ามนับสิ่งที่คิด/ทดลองแต่ไม่ได้ส่งเป็นคำตอบครบ
4. ชุดกว้างของ Aetox ไม่เขียว: engine หมดเวลา 8 นาทีใน `TestRemovingContextDeletesTheFileAndAnswersWithWhatIsLeft`; skill มี `TestImpactLiveRealGopls` timeout และ `TestEveryFileToolFindsWhatWritePlaced` cleanup ถูกล็อก เทสต์เฉพาะส่วนที่ปรับผ่าน ไม่ขยายไปแก้ปัญหาเหล่านี้
5. ค่าใช้จ่ายรายงาน `priced=false` จึงไม่ใช้ `$0` เป็นค่าบิล และช่วงรัน Gin ก่อนมีชุด unit test กว้างทำงานพร้อมกัน จึงไม่ใช้เวลารันนั้นยืนยันเปอร์เซ็นต์ความเร็ว

## ข้อสรุปรอบนำร่อง

ลดขั้นตอนบางอย่างในงานเล็กและการไล่ CI ที่ไม่เกี่ยวได้ แต่ยังมีงานซ้ำระหว่างตัวหลักกับลูกมือ พิธีแผนที่ผู้ใช้ไม่ได้ขอ และการส่งงาน/รับ feedback ที่ถดถอย ไม่ควรเรียกการปรับนี้ว่าสำเร็จเพียงเพราะเวลา จำนวนเทสต์ หรือจำนวนคำขอลดลง ยังไม่ได้เพิ่มกฎหรือปรับพรอมต์รอบใหม่จากผลนี้
