# แถบความคิดตอนคิด — ย้อนอ่านได้แค่ไหน และทำยังไงให้ได้คืน

**สถานะ: ข้อเสนอ ยังไม่ตัดสิน · 11 ก.ย. 2026**

## ที่ทำไปแล้วรอบนี้

กล่อง `.reasoning-body.live` เคยถือข้อความที่โมเดลคิดมาทั้งหมดไว้ใน DOM (ที่เห็น 5 บรรทัดเป็น CSS cap) ทุกเฟรมจึงเขียนทั้งก้อน + อ่าน `scrollHeight` + เลื่อนกล่อง งานต่อเฟรมโตตามความยาวของเทิร์น วัดจริง 300 เฟรม/ขนาด:

| คิดมาแล้ว | เดิม (ms/เฟรม) | ใหม่ (ms/เฟรม) | งบ 1 เฟรม @60Hz |
|---|---|---|---|
| 10 KB | 1.0 | 0.7 | 16.7 |
| 40 KB | 4.5 (p95 7.9) | 0.8 | 16.7 |
| 120 KB | 13.2 (p95 **28.8**) | 1.4 | 16.7 |
| 300 KB | **35.5** (p95 70.4) | 0.8 | 16.7 |

ตอนนี้ DOM ถือแค่ท้าย ~4,000 ตัวอักษร (`THINK_TAIL_CHARS`) + รวม rAF ให้วาดเฟรมละครั้ง + ตัดที่ขอบบรรทัด · จังหวะตัวอักษรและจำนวนเฟรมไม่เปลี่ยน — ที่เปลี่ยนคืองานในแต่ละเฟรม

## ปัญหาที่เหลือ

1. **ย้อนอ่านได้จำกัด** — ระหว่างเทิร์น เลื่อนขึ้นได้ ~40 บรรทัดท้าย (เดิมได้ทั้งหมด) จบเทิร์นแล้วแผงเต็มยังมีครบ
2. **ตอนเลื่อนอ่าน ข้อความเลื่อนหนี** — ของใหม่ตัดหัวทิ้งทุกเฟรม ข้อความที่ตากำลังอ่านจึงไถลขึ้น (ของเดิมต่อท้ายอย่างเดียว ตำแหน่งที่อ่านจึงนิ่ง)

ข้อ 2 สำคัญกว่าข้อ 1 เพราะคอมเมนต์เดิมของกล่องนี้เขียนไว้เองว่า *"it still scrolls — wheel, touchpad and keyboard all reach the earlier lines"* — ของใหม่ทำให้ประโยคนั้นจริงแค่ 4,000 ตัวอักษร และไม่นิ่งด้วย

## กลไกที่เสนอ: "กำลังอ่าน = ตรึงภาพ"

`thinkPinned` มีอยู่แล้ว (unpin ตอนผู้ใช้เลื่อนขึ้น, pin กลับเมื่อถึงล่าง) ใช้เป็นสวิตช์ได้เลย:

> **ขณะ unpin — ให้กล่องวาด "ภาพนิ่ง" ของข้อความ ณ วินาทีที่เริ่มอ่าน** ไม่ใช่สตรีมที่ไหลอยู่

ผลที่ได้ฟรีสามอย่าง:
- **ตำแหน่งที่อ่านนิ่ง** — ข้อความที่ส่งเข้า pacer ไม่เปลี่ยนแล้ว จึงไม่มีอะไรถูกตัดหรือเลื่อน
- **งานต่อเฟรมของกล่อง = 0** ระหว่างอ่าน (`feed` เห็นข้อความเดิมแล้ว return) เหลือแต่งานของหน้าเว็บที่มีอยู่แล้ว
- **ไม่มี state ใหม่ใน pacer เลย** — เป็นแค่ "ส่งข้อความก้อนไหน" จาก Chat.svelte ไม่ต้องเพิ่ม `hold` หรือธงอะไร

ตอนผู้ใช้เลื่อนกลับล่างสุด: ส่งสตรีมจริงกลับเข้าไปตามเดิม ข้อความที่เลยไปจะไหลตามทันใน ~400ms (กลไกเดิมของ pacer) หรือจะกระโดดไปท้ายสุดทันทีก็ได้ — เป็นดีลข้อ 3 ด้านล่าง

## ดีลที่ต้องเลือก 3 ข้อ

| # | ดีล | ตัวเลือก | ผล |
|---|---|---|---|
| 1 | ภาพนิ่งนั้นเป็นข้อความเต็มหรือแค่ท้าย | **เต็ม** = ย้อนอ่านได้ทั้งหมดระหว่างเทิร์น แลกกับ 1 เฟรมแพง (~35ms ที่ 300KB = เฟรมเดียว ตามองไม่ทัน) ตอนเริ่มตรึง · **ท้าย 4,000** = ฟรี แต่ย้อนได้เท่าเดิม | ข้อ 1 ของปัญหา แก้หรือไม่แก้ |
| 2 | กล่องสูงขึ้นไหมตอนตรึง | ตอนนี้ `max-height:7.5em` = 5 บรรทัด อ่านยาวๆ ทรมาน · ขยายเป็นเช่น 40vh เฉพาะตอนตรึง (CSS + ตั้ง `scrollTop` ให้บรรทัดที่อ่านอยู่ไม่กระโดด) | ประสบการณ์ตอนอ่าน |
| 3 | ตอนปล่อย (กลับไปล่าง) | **ไหลตามทัน** ~400ms (กลไกเดิม ต่อเนื่องกว่า) หรือ **กระโดด** ไปท้ายสุด (ตรงไปตรงมา — สิ่งที่เลยไปคือสิ่งที่ผู้ใช้เลือกไม่ดู) | ความรู้สึกตอนกลับ |

ทั้งสามข้อรวมกันเป็นงานชิ้นเดียว ประมาณ: Chat.svelte ~15 บรรทัด + CSS 2 บรรทัด + เทสต์ 2-3 ข้อ — **ไม่แตะ streamPace.ts เลย**

## ทางเลือกอื่น และทำไมไม่แนะนำ

- **ขยายหน้าต่างเฉยๆ (8,000 / 16,000)** — วัดแล้ว 1.8 / 3.1 ms ต่อเฟรม แก้ข้อ 1 ได้บางส่วน (ย้อนได้ 2-4 เท่า) แต่**ไม่แก้ข้อ 2 เลย** ตัวที่ทำให้อ่านไม่นิ่งคือการตัดหัว ไม่ใช่ขนาดหน้าต่าง ควรใช้เป็นตัวปรับคู่กันได้ แต่ไม่ใช่คำตอบ
- **virtualize รายการทั้งก้อน** — เป็นวิธีที่ถูกสำหรับ log ยาว แต่กล่องนี้สูงแค่ 5 บรรทัด พื้นที่ให้ประหยัดแทบไม่มี แลกกับงานวัดความสูงบรรทัดที่พันกัน (`pre-wrap` ตัดบรรทัดเอง) — ไม่คุ้ม
- **ไม่ทำอะไร** — ยอมรับได้ เพราะรอจบเทิร์นก็ได้ครบ และคนส่วนใหญ่ไม่เลื่อนอ่านระหว่างคิด แต่ต้องรู้ตัวว่าคำโฆษณาเดิมของกล่อง ("scroll back to the earlier lines") จะจริงแค่ 40 บรรทัด

## สิ่งที่ควรวัดก่อนตัดสิน (อาจพลิกลำดับความสำคัญ)

กล่องความคิดเป็นของที่ **เพิ่งแก้แล้ว** แต่ยังมีที่เดียวกันอีกจุดที่ยังไม่ได้วัด: **ข้อความคำตอบ** (`pacedStream` → marked + DOMPurify + highlight.js) ซึ่งรันใหม่ทุกครั้งที่มีอักษรเพิ่ม และคอมเมนต์ใน `markdown.ts` เขียนเองว่าวัดได้ **12 ms ที่ 7.5 KB** — ต่างจากกล่องความคิดตรงที่อันนี้ **จ่ายทุกเทิร์น** และคำตอบยาวๆ อยู่บนจอถาวร

ถ้าตัวเลขนั้นจริงและโตตามความยาว (ยังไม่ยืนยัน) มันจะใหญ่กว่าปัญหาย้อนอ่านข้างบนนี้ — ควรวัดก่อน แล้วค่อยตัดสินว่าจะเอางบไปลงที่ไหน (วัดด้วยหน้าม้านเดิม: `scratch/think-tail-bench.html` ขยายให้ครอบเส้นทาง markdown)

อีกจุดที่ยังไม่แตะ: `l.reasoningText += chunk` ใน `cockpit.svelte.ts` — ทุกก้อนคัดลอกสตริงทั้งก้อน (300KB × ทุก chunk) เป็นที่เดียวที่งานยังโตตามความยาวเทิร์นจริงๆ แต่แตะ store จึงต้องดูผลข้างเคียงก่อน

## คำแนะนำ

1. **วัดราคาของคำตอบก่อน** (ครึ่งวันถ้านับการเขียนเทสต์) — เพราะตัวเลขนั้นอาจทำให้ข้อเสนอทั้งหมดข้างบนกลายเป็นเรื่องรอง
2. แล้วค่อยทำกลไก "ตรึงภาพ" ทั้งชุด โดยเลือกดีล 1 = **เต็ม**, 2 = **ขยายกล่อง**, 3 = **ไหลตามทัน** — ได้ทั้งความลื่น งานต่อเฟรม 0 ระหว่างอ่าน และย้อนอ่านได้เท่าเดิมที่เคยมี
