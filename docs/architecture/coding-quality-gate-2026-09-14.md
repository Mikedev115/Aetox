## 0. ทำไม

การทดลองของผู้ทดสอบ: GPT-5.6 Luna / low ทั้งสองฝั่ง, workspace แยก, prompt เดียวกัน,
ห้าม skill/team/sub-agent, hidden tests อิสระหลังจบ — Aetox ชนะ behavioral completion
ทั้งสองรอบ **ทั้งที่โมเดลเท่ากัน** นั่นคือ harness มีผลจริง และสองย่อหน้าใน
[coding.md](../../internal/mode/modes/coding.md) ที่ทำให้ต่างคือ *"A turn ends when
the work is done, not when a plan for it is written"* (§222) กับ *"Done means proven by
execution"* — สองย่อหน้านี้เป็นของที่**ห้ามแตะโดยไม่วัดผล** และเอกสารนี้ไม่แตะ

จุดอ่อนที่เขาชี้: `server.ts` เหลือ 9 บรรทัด บรรทัดยาวสุด 1,822 ตัวอักษร,
`queue.ts` 958 — ถูกต้องเชิงพฤติกรรม อ่านไม่ได้เชิงโค้ด

สาเหตุอยู่ที่เราเอง และแก้ไปแล้วเป็น §264 (`ff617358`): เพดาน 300 บรรทัดที่นับแค่
newline สอนโมเดลระดับ low ว่า "บรรทัดคือของแพง" ตอนนี้นับตามความกว้าง (120 ตัวอักษร
= 1 บรรทัด) และคำอธิบายบอกว่าการยุบไม่ซื้ออะไร วัดซ้ำคืนเดียวกันด้วยโจทย์รูปเดียวกัน
(node:http server + priority queue + tests, โฟลเดอร์ว่าง, gpt-5.6-luna ผ่าน codex):

| รอบ | think | `server.ts` | `queue.ts` | tests | เวลา |
|---|---|---|---|---|---|
| ผู้ทดสอบ | low | 9 บรรทัด / ยาวสุด **1,822** | ยาวสุด 958 | — | — |
| หลัง §264 | max | 323 / ยาวสุด 92 | 260 / 82 | 11 เขียว | 27.5 นาที |
| หลัง §264 | low | 50 / ยาวสุด **161** (5 บรรทัดเกิน 120) | 71 / 114 | 5 เขียว | 4 นาที |

การยุบ*ทั้งไฟล์*หายไป แต่ที่ระดับ low ยังเหลือการยุบ*คำสั่ง* — ห้าบรรทัดแบบ
`if (...) return send(res, 404, {...});` และ `const job = ...; return job ? ... : ...;`
เพดานมองไม่เห็นมัน (50 บรรทัดกว้าง ~60 ยังห่าง 300 ลิบ) และ**ไม่ควรเห็น** — เพดาน
คือเรื่องขนาดผลลัพธ์ ไม่ใช่เรื่องสไตล์ สิ่งที่คลี่ห้าบรรทัดนั้นคือ formatter และสิ่งที่
ทำให้ formatter ถูกรัน*ก่อน*โมเดลพูดว่า "เสร็จ" คือประตูที่เอกสารนี้ออกแบบ

ทำไมไม่ใส่ประโยคใน coding.md ให้จบ ๆ: เพราะนั่นคือไฟล์ที่เพิ่งพิสูจน์ว่าเป็นจุดแข็ง
และ prompt คือการ*ขอ* ไม่ใช่การ*ตรวจ* — ผู้ทดสอบเองก็เขียนว่า *"build/typecheck/test/
integration/startup smoke ต้องผ่านก่อน agent ประกาศ Done"* ซึ่งเป็นกลไก ไม่ใช่ถ้อยคำ

## 1. ศึกษาจากใคร แล้วเอาอะไรมา ไม่เอาอะไร

อ่านสี่ระบบที่ทำเรื่องนี้จริง (14 ก.ย.) ตามกฎ [adapt-owner-repo-ideas]: บอกให้ชัดว่า
หยิบอะไร ทิ้งอะไร

**Aider — auto-lint / auto-test** ([docs](https://aider.chat/docs/usage/lint-test.html)).
หลัง LLM แก้ไฟล์ทุกครั้ง รัน linter ของภาษานั้น (มี built-in ต่อภาษา) และถ้าตั้ง
`--test-cmd --auto-test` ก็รันเทส exit ≠ 0 → ป้อน output กลับให้แก้
- เอามา: **สัญญาที่เรียบที่สุดที่เป็นไปได้** — คำสั่งหนึ่งบรรทัด, exit code คือคำตัดสิน,
  stdout/stderr คือเหตุผล ไม่มี JSON protocol ไม่มี plugin
- ไม่เอา: จังหวะ "หลังทุก edit" — เทส 2 นาทีหลังไฟล์ทุกไฟล์คือหายนะ และ aider ไม่มี
  แนวคิด "Done" ให้ค้าน มันแค่แก้ไปเรื่อย ๆ

**Claude Code — `Stop` hook** ([docs](https://code.claude.com/docs/en/hooks)). ยิงตอน
โมเดลจะจบเทิร์น สคริปต์ผู้ใช้ตอบ exit 2 หรือ `{"decision":"block","reason":"…"}` →
โมเดล**ถูกบังคับให้ทำต่อ**พร้อมอ่าน reason; `stop_hook_active` กันลูป
- เอามา: **จังหวะ** — ตรวจตอนจะ Done เท่านั้น เพราะเป็นจุดเดียวที่มีคำว่า "เสร็จ" ให้
  ค้าน และ verdict เข้าไปเป็น user turn (Aetox มีช่องนี้แล้ว: `OnGoalCheck`)
- ไม่เอา: ผู้ใช้ต้องเขียนสคริปต์เองทั้งหมด (คนทั่วไปทำไม่ได้ — ผู้ทดสอบขอ "ให้ผู้ใช้
  กำหนด policy" ไม่ใช่ "เขียนโปรแกรม"), reason เป็น prose อิสระที่โมเดลเถียงได้, และ
  กันลูปด้วย flag เดียว = บล็อกได้จริงครั้งเดียว

**OpenCode — formatter อัตโนมัติ** ([architecture-reference-opencode.md](../architecture-reference-opencode.md) §Formatters).
ทุกครั้งที่ edit จบ รัน formatter ทับไฟล์เลย โมเดลไม่รู้ ไม่มี verdict
- เอามา: **format คือ fix ไม่ใช่ check** — ปัญหาบรรทัดยาวไม่ควรกลายเป็นรอบสนทนา
  ทำให้เลยแล้วบอกบรรทัดเดียว
- ไม่เอา: ทำเงียบสนิท — โมเดลที่ไม่เห็นว่าไฟล์ถูกจัดใหม่ไม่เคยเรียนรู้ว่ามันเขียนมา
  ผิด และไม่ได้ครอบ build/test

**pre-commit + CI required checks** — โลกมนุษย์
- เอามา: **policy เป็นไฟล์ในรีโป** เดินทางกับโค้ด ทีมใช้ชุดเดียวกัน — นี่คือสิ่งที่
  ผู้ทดสอบขอตอนพูดถึง Coding Profile "ย้ายข้ามเครื่องหรือแชร์กันได้" เขาไม่ได้ขอไฟล์
  ตั้งค่าของ Aetox เขาขอไฟล์ในโปรเจกต์; และ**ผลเป็นรายการ check ✓/✗** ไม่ใช่ย่อหน้า
- ไม่เอา: ผูกกับ git commit — Aetox ปิดเทิร์นบ่อยกว่า commit มาก

**ของเราเอง — มุ่งเป้า gate 1/3** ([goal_run.go](../../internal/engine/goal_run.go)).
หลักที่เขียนไว้แล้วและใช้ตรงนี้ได้ทั้งดุ้น: *"a gate that can fire repeatedly on prose
is a gate that argues"* — gate ต้อง mechanical (มีแถว/ไม่มีแถว, exit 0/ไม่ 0) ส่งกลับ
พร้อม**ชื่อสิ่งที่ค้าง** ไม่ใช่ความเห็น, มีเพดาน `sentBack`, และ progress ไปอยู่บนจอ
ไม่ใช่ในบทสนทนา (narration ราคา quadratic)

## 2. ขอบเขตที่ตัดสินใจแล้ว

1. **Gate คือ mechanical เท่านั้น** — ทุก check คือคำสั่งที่รันแล้วดู exit code
   ไม่มี check ชนิด "ให้โมเดลอีกตัวดู" ในเฟสนี้ (§6 ข้อ reviewer)
2. **Opt-in ต่อโปรเจกต์** — ไม่มีไฟล์ = ไม่มี gate ผู้ใช้ที่ไม่รู้จักฟีเจอร์นี้ต้องไม่ถูก
   บล็อกโดยไม่รู้ตัว (เหตุผลเดียวกับ `Blocking` ของ hook ที่ off by default)
3. **ยิงที่ปลายเทิร์นของโต๊ะโค้ด** ไม่ใช่หลังทุก write, ไม่ใช่ทุกโต๊ะ — ผู้ช่วย/
   specialized ไม่มี "โค้ดที่ต้องผ่าน" ให้ตรวจ
4. **ไม่แตะ coding.md** — ประตูไม่ต้องขอให้โมเดลทำอะไรเพิ่ม เพราะประตูทำเอง
5. **Format คือ fix** — check ที่ประกาศ `fix: true` เขียนทับไฟล์ได้ และไม่นับเป็น ✗
   ถ้าหลัง fix แล้วรันซ้ำผ่าน
6. **ไม่ใช่ hook** — hook (10 s, ระหว่างทาง, ต่อ tool call) กับ gate (นาที, ปลายทาง,
   ต่อเทิร์น) คนละจังหวะ คนละ budget อยู่คนละแพ็กเกจ; hook ยังอยู่เหมือนเดิมสำหรับ
   คนที่อยากได้แบบ aider ต่อไฟล์ (go-check.ps1 คือตัวอย่างที่ใช้ได้อยู่แล้ว)
7. **Remote engine (§248)**: check รันในโปรเซส engine เสมอ ซึ่งคือเครื่องที่โค้ดอยู่
   โดยนิยาม — ไม่มีทางเลือกอื่นให้ออกแบบ แต่ต้อง*เขียนไว้*เพราะหน้าจอที่แสดงตารางอยู่
   อีกเครื่อง

## 4. รูปร่าง

### 4.1 Policy: ไฟล์ในโปรเจกต์

`.aetox/gate.yaml` ที่ root ของโปรเจกต์ (ควบคู่ AETOX.md ไม่ใช่ใน AETOX.md — AETOX.md
เป็นร้อยแก้วสำหรับโมเดล gate.yaml เป็นข้อมูลสำหรับเครื่อง ผสมกันแล้วทั้งสองอย่าง
อ่านยาก) รูปแบบตั้งใจให้เล็กพอที่คนไม่เขียนโปรแกรมพิมพ์ได้ และ Aetox **เสนอสร้างให้**
เมื่อเห็น `package.json` / `go.mod` / `pyproject.toml` ครั้งแรกในโปรเจกต์ที่ยังไม่มี

```yaml
# .aetox/gate.yaml — สิ่งที่ต้องผ่านก่อนเอเจนบอกว่าเสร็จ
checks:
  format:    { run: "npx prettier --write .", fix: true }
  typecheck: { run: "npx tsc --noEmit" }
  test:      { run: "npm test", timeout: 300 }
style:
  max_line: 120          # ตรวจกับไฟล์ที่เทิร์นนี้แตะเท่านั้น
sent_back_max: 3         # ค่าเริ่มต้น; 0 = แค่รายงาน ไม่ค้าน
```

- `run` รันผ่าน shellBackend ของโปรเจกต์ที่ root; exit 0 = ✓
- `fix: true` = รันแล้วไฟล์อาจเปลี่ยน; ไม่นับเป็น ✗ จาก exit code (prettier/gofmt คืน 0
  อยู่แล้ว แต่บาง formatter คืน 1 เมื่อมีการแก้ — aider เจอปัญหาเดียวกันและบอกให้ห่อ
  สคริปต์ เราไม่ให้ผู้ใช้ห่อ) ถ้าไฟล์เปลี่ยน โมเดลได้บรรทัดเดียว: *"format จัด 2 ไฟล์
  ให้แล้ว: src/server.ts, src/queue.ts"*
- `timeout` ต่อ check ค่าเริ่มต้น 120 s; เกินแล้วคือ ✗ พร้อมเหตุผล "หมดเวลา" ไม่ใช่ค้าง
- `style.max_line` เป็น check ในตัวชนิดเดียวที่ไม่ต้องมีคำสั่ง เพราะไม่ทุกภาษามี
  formatter ที่ห้ามบรรทัดยาว — วัดเฉพาะไฟล์ที่ change tool แตะในเทิร์นนี้ (รายชื่อมีอยู่
  แล้วใน filestate) ไม่ใช่ทั้งรีโป
- check ทำงานตามลำดับที่เขียน; `fix` ควรอยู่บนสุดเพื่อให้ typecheck/test เห็นไฟล์ที่
  จัดแล้ว; ตัวแรกที่ ✗ ไม่หยุดตัวถัดไป — ตาราง CI แสดงทุกแถว

### 4.2 จังหวะ: ต่อคิวหลังมุ่งเป้า บนช่องเดียวกัน

ปลายเทิร์นของโต๊ะโค้ด ถ้าโปรเจกต์มี gate.yaml และเทิร์นนี้**แตะไฟล์อย่างน้อยหนึ่ง**
(เทิร์นที่แค่อ่าน/ตอบคำถามไม่มีอะไรให้ตรวจ — ประหยัดเวลา และไม่ทำให้ "อธิบายโค้ด
หน่อย" ต้องรอ npm test) → รัน checks → ถ้าทุกแถว ✓ คืน `""` ปล่อยจบ; ถ้ามี ✗ คืน
verdict (§4.3)

ลำดับบนช่อง `OnGoalCheck`: **มุ่งเป้าก่อน gate** — ถ้ามุ่งเป้าค้าน (step ค้าง/ยังไม่มี
report) ก็ยังไม่ต้องเสียเวลารันเทส เพราะงานยังไม่ถึงจุดที่มีอะไรให้ตรวจ; gate ถามเมื่อ
มุ่งเป้าพอใจแล้วหรือไม่ได้เปิดอยู่ ทำเป็น `composeChecks(goal, gate)` ไม่ใช่ช่องที่สอง
เพราะ agent.go ควรรู้จัก "ผู้ค้าน" แค่คนเดียวต่อไป

### 4.3 Verdict: ตาราง ไม่ใช่ย่อหน้า

สั้น mechanical ชื่อสิ่งที่ค้าง — แบบ `unfinishedVerdict` ของมุ่งเป้า:

```
[gate] ยังไม่ผ่าน 2 จาก 4:
  ✓ format      (จัด 2 ไฟล์ให้แล้ว)
  ✗ typecheck   exit 2, 1.8s — src/server.ts(32,7): error TS2322 …  (+2 บรรทัด)
  ✗ test        exit 1, 14s — 1 failing: "cancel queued, running, and completed jobs"
  ✓ style       ไม่มีบรรทัดเกิน 120
งานยังไม่จบ แก้แล้วจบเทิร์นอีกครั้ง (ส่งกลับครั้งที่ 1 จาก 3)
```

- output ของ check ที่ ✗ ถูกตัดเหลือ **บรรทัดที่บอกอะไร** (error/FAIL/not ok/exit)
  ไม่เกิน ~20 บรรทัดต่อ check — output เต็มไปอยู่บนจอ (§4.4) โมเดลอ่านต่อได้ผ่าน
  `shell output` ถ้าต้องการ เหตุผล: verdict ถูก re-send ทุกรอบที่เหลือของเทิร์น
- ไม่มีคำแนะนำว่าควรแก้ยังไง — นั่นคือ prose และ prose คือสิ่งที่ถูกเถียง

### 4.4 เพดานและทางออก (คำตอบข้อ 1 ของ §5)

`sent_back_max` ครั้ง (ค่าเริ่มต้น 3) เมื่อถึงเพดานแล้วยัง ✗ — **ถามผู้ใช้** ผ่านการ์ด
เดียวกับที่โต๊ะโค้ดถามเรื่องอื่น (blocking question): *"gate ยังไม่ผ่านหลังพยายาม 3
รอบ: test ✗ — จะให้ (ก) ลองต่อ (ข) จบเทิร์นพร้อมบันทึกว่า test ยังไม่ผ่าน (ค) หยุด"*

ไม่ใช่ "ปล่อยพร้อม known limitation อัตโนมัติ" ตามที่ผู้ทดสอบเสนอ ด้วยเหตุผลที่
เจ้าของเห็นด้วย: *ยอมแพ้แล้วจดไว้* คือทางออกที่โมเดลจะเรียนรู้ที่จะเลือกเร็วขึ้นเรื่อย ๆ
และ §17 ห้ามระบบตัดสินแทนคนในเรื่องที่คนควรตัดสิน ตัวเลือก (ข) ยังมีอยู่ — แต่เป็นคน
กด ไม่ใช่โมเดลเลือก และเมื่อกด ข้อความ known limitation ถูกเขียนลงตารางบนจอโดยระบบ
(check ไหน, output อะไร, ใครยอม, เมื่อไร) ไม่ใช่โมเดลแต่งเอง

### 4.5 บนจอ

การ์ดเล็กใต้คำตอบสุดท้ายของเทิร์น: ชื่อ check, ✓/✗, เวลา, คลิกเปิด output เต็ม
— รูปเดียวกับหน้า checks ของ PR ที่ทุกคนเคยเห็น ไม่ใช่ข้อความในแชต ระหว่างที่ gate
รัน (อาจหลายสิบวินาที) การ์ดแสดง "กำลังตรวจ…" พร้อมแถวที่วิ่งอยู่ เพื่อไม่ให้หน้าจอ
ดูเหมือนค้างหลังโมเดลพิมพ์คำตอบเสร็จ — นี่คือจุดที่ต่างจากมุ่งเป้า: gate ใช้เวลา*จริง*
หลังคำตอบปรากฏ ผู้ใช้ต้องรู้ว่าทำไมยังไม่ถือว่าจบ

Event: `gate:update` `SessionEvent[GateReport]` ตามแบบ `plan:update`; แถวถูกเก็บ
ลง DB ต่อเทิร์น (แบบ `plan_reports`) เพื่อให้ชิ้นงาน/ประวัติเปิดดูย้อนหลังได้ และเป็น
ที่ที่ Coding Profile (§6) จะอ่านสถิติ

## 5. คำถามสี่ข้อ และคำตอบที่ตกลงกัน (14 ก.ย.)

1. **gate ปิดเทิร์นได้แค่ไหน?** → ค้านได้ไม่เกิน `sent_back_max` แล้ว**ถาม** ไม่ปล่อย
   เอง (§4.4)
2. **ขยาย hook timeout หรือแยก?** → **แยก** — gate เป็นแพ็กเกจของตัวเอง
   (`internal/gate`) ไม่ใช่ event ที่สามของ hook; hook ยังเป็น 10 s ต่อ tool call
3. **remote engine?** → รันในโปรเซส engine เสมอ = เครื่องที่โค้ดอยู่; หน้าจอรับแค่
   `gate:update` เหมือน event อื่นข้าม rpc (§248) — ไม่มีอะไรพิเศษให้ทำ แต่ต้องมีเทส
   ว่า path ใน verdict เป็น path ของฝั่ง engine
4. **reviewer/tester อิสระ?** → **ไม่ทำในเฟสนี้** gate mechanical ให้ ~80% ของค่า
   และ reviewer ที่เป็นโมเดลคือ "gate that argues" ตัวจริง ที่ว่างไว้: check ชนิด
   `agent:` (§6)

## 6. ที่วางไว้ให้ข้อเสนออีกสองข้อ (ไม่ทำในเฟสนี้)

**reviewer / tester ที่เป็นอิสระ** — ผู้ทดสอบขอสามกฎ: worker ห้ามตัดสินงานตัวเอง,
reviewer ห้ามแก้ source, tester ห้ามลด assertion เมื่อถึงเวลา ทั้งสามคือ **tool scope
ต่อบทบาท** ซึ่ง desk scope ทำอยู่แล้วต่อโต๊ะ — reviewer = โต๊ะโค้ดที่ไม่มี `change`,
tester = โต๊ะโค้ดที่ `change` แตะได้เฉพาะ `test/**` และ `edit` ที่ลด `assert` ถูก
PreToolUse ปฏิเสธ (kind ของกฎที่ safety.go ทำอยู่แล้วกับ shell) ใน gate.yaml จะโผล่
เป็น `review: { agent: reviewer, must: PASS }` — check ชนิดที่รันเอเจนแทนคำสั่ง
ทำ**หลัง**เฟสนี้เพราะ (ก) เป็น "gate that argues" ต้องมีเพดานและ UI ของตัวเอง
(ข) ราคาเป็น model call ต่อเทิร์น ซึ่ง §106.10 ปฏิเสธมาแล้วครั้งหนึ่ง ต้องมีตัวเลขว่า
mechanical gate ไม่พอก่อน

**Coding Profile ส่งออก/นำเข้า** — ผู้ทดสอบขอ "main-agent policy + sub-agent
models/prompts/step limits + quality gates เป็นไฟล์เดียว" ครึ่งหนึ่งของนั้นมีอยู่แล้วเป็น
ไฟล์ในรีโป (AETOX.md, `.aetox/gate.yaml`, `agents/*/AGENT.md` ที่ agentpkg แพ็กได้) —
Profile คือ**มัด**ของไฟล์เหล่านั้นหนึ่งชั้นเหนือ agentpkg ตามกฎเดียวกัน (declare ไม่
grant; หนึ่งคำถามหนึ่งคำตอบบนดิสก์) ทำได้ต่อเมื่อ gate.yaml มีตัวตนแล้ว จึงมาหลัง
