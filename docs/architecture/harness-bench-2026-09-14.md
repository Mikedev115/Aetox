# วัด harness — Aetox เทียบเครื่องมือโค้ดตัวอื่นบนโมเดลเดียวกัน (2026-09-14)

Direction document, เขียนก่อนลงมือ — ยังไม่ได้ติดตั้งคู่แข่งตัวไหน ยังไม่ได้เขียนโจทย์
ยังไม่มีตัวเลขสักตัว [BENCHMARK.md](../../BENCHMARK.md) วัดแต่ "แอป" (ดิสก์ · RAM ·
เวลาเปิด) ส่วนนี้วัดสิ่งที่ผู้ใช้จ่ายเงินซื้อจริง ๆ: **เมื่อโมเดลเดียวกันนั่งอยู่ในเครื่องมือคนละตัว
งานเสร็จต่างกันแค่ไหน**

ต้นเรื่องคือรายงานของผู้ทดสอบภายนอก (DECISIONS §264, 13 ก.ย. 2026): Aetox ชนะ Codex
สองรอบบน GPT-5.6 Luna ที่ low ทั้งสองฝั่ง เขาอ่านถูกว่านั่นคือ harness ไม่ใช่โมเดล — แต่
สองรอบบอกได้แค่ทิศ บอกขนาดไม่ได้ และเทียบไว้เจ้าเดียว เอกสารนี้คือแบบที่จะทำให้ตัวเลขนั้น
ยืนได้เอง

กฎข้อเดียวของ BENCHMARK.md ใช้กับที่นี่เต็ม ๆ: **ตัวเลขที่ยังไม่ผ่านกติกาใน §5 ห้ามขึ้น README
หรือแลนดิ้ง** ผลรอบครึ่ง ๆ อยู่ในไฟล์นี้เท่านั้น

Status: **`Proposed`** — เจ้าของสั่ง *"ลิสมาก่อน ทำเป็นเอกสารมาก่อน"* (14 ก.ย. 2026)

## 1. คำถามที่วัด และที่ไม่วัด

**วัด:** ถือโมเดลคงที่ เปลี่ยน harness — งานเสร็จกี่ส่วน โค้ดที่ได้อยู่ในสภาพไหน ใช้กี่รอบ
กี่โทเค็น นี่คือ "harness effect" ที่ §264 เห็นแล้วแต่ยังไม่ได้วัด

**ไม่วัด (รอบนี้):**

| คำถาม | ทำไมไม่ใช่รอบนี้ |
|---|---|
| โมเดลไหนดีสุดใน Aetox | คนละตัวแปร — ถ้าเปลี่ยนทั้งโมเดลทั้ง harness พร้อมกัน ตารางบอกอะไรไม่ได้ ทำเป็นรอบสองหลังรอบนี้จบ |
| โมเดล local (LM Studio / Ollama) | งาน agentic บน 8 GB VRAM ล้มเพราะโมเดล noise กลบ harness — เป็นคำถาม "Aetox ทำให้โมเดลเล็กใช้งานได้แค่ไหน" ซึ่งดีแต่เป็นคนละคำถาม |
| สกิล · ทีม · sub-agent · MCP | ปิดหมดทุกฝั่ง Aetox ต้องแข่งในสภาพเปล่าเท่าคนอื่น (ผู้ทดสอบ §264 ก็ปิด) |
| Claude Code · Gemini CLI · Copilot CLI · Cursor · Amp | ล็อกโมเดลของตัวเอง ไม่มีทางให้ Aetox ใช้โมเดลเดียวกันด้วยบัญชีเดียวกัน — แถว `anthropic` ใน [catalog.go](../../internal/provider/catalog.go) รับแต่ API key ไม่มีทางล็อกอินด้วยแผน |

## 2. คู่ที่เทียบ — 4 คู่ 2 โมเดล

หลัก: **คู่แข่งเป็นคนบังคับโมเดล** และโมเดลต้องเป็นตัวที่เจ้าของมีอยู่แล้วโดยไม่ซื้อเพิ่ม

| คู่ | โมเดลที่ล็อก | ระดับคิด | แกนที่คู่นี้ตอบ |
|---|---|---|---|
| Aetox vs **Codex** | GPT-5.6 Luna ผ่านล็อกอิน ChatGPT เดียวกัน | low ทั้งสองฝั่ง | โมเดลแบบสมัครสมาชิก · ต่อจากข้อมูล §264 ได้ตรง ๆ |
| Aetox vs **OpenCode** | DeepSeek (คีย์เดียวกัน) | ปิดคิด / ต่ำสุดที่ทั้งสองฝั่งมี | harness ยอดนิยมสาย BYOK |
| Aetox vs **Crush** (Charm) | DeepSeek | เดียวกัน | harness ที่โครงใกล้ Aetox ที่สุด (Go · ตัวต่อของ opencode-go) — ถ้าต่างกันคือ harness ไม่ใช่ภาษา |
| Aetox vs **Aider** | DeepSeek (`deepseek/deepseek-chat`) | เดียวกัน | **ไม่มี agent loop** — repo-map + diff edit ตอบว่า loop ของ Aetox ให้อะไรเหนือกว่าแก้ไฟล์ตรง ๆ |

ที่พิจารณาแล้วไม่เอา: Goose (ซ้ำกับ OpenCode/Crush เว้นแต่จะวัด MCP) · Qwen Code (fork
Gemini CLI ไม่เพิ่มความรู้) · Cline/Roo (VS Code extension สั่งรัน 30 รอบแบบสคริปต์ไม่ได้
ชนกติกา "วัดมือแล้วจดไม่นับ") · Hermes (เก็บไว้ถ้าอยากปิดลูป study → วัด)

**ข้อที่ต้องจดในกติกา:** Aetox คุย DeepSeek ผ่าน `/anthropic` ([catalog.go:526](../../internal/provider/catalog.go)) ส่วนสามเจ้าที่เหลือผ่าน OpenAI-compatible — endpoint ต่างกัน
โมเดลเดียวกัน ยอมรับได้แต่ต้องเขียนไว้ ไม่งั้นมีคนทักได้และทักถูก

## 3. โจทย์ — 5 งาน 5 รูปร่าง

หลักการเลือก: งานหนึ่งรูปร่างหนึ่ง แต่ละรูปร่างเปิดเผยด้านหนึ่งของ harness ที่รูปร่างอื่นไม่เปิด
ผสม TS กับ Go เพราะผล §264 เป็น TS ล้วน — ถ้า Aetox ชนะแต่ TS ก็ต้องรู้

ทุกงาน: มี **เทสซ่อน** ที่เขียนเสร็จและ commit ก่อนรันรอบแรก harness เห็นแต่โจทย์ · ปิด
เว็บทุกฝั่ง (โจทย์ที่มาจาก commit จริงค้นเจอได้) · ไม่มีข้อความตามหลังจากคน ยกเว้นคำตอบที่
สคริปต์เตรียมไว้ในงานที่ 5

### งาน 1 — สร้างจากศูนย์ (TypeScript) · "คิวงานหลัง HTTP"

| | |
|---|---|
| โจทย์ | โปรเจกต์เปล่า มี `package.json` + vitest ตั้งไว้แล้ว ให้เขียน HTTP service: `POST /jobs` รับงาน · `GET /jobs/:id` ดูสถานะ · worker ทำงานพร้อมกันไม่เกิน N · ล้มแล้ว retry พร้อม backoff · สถานะรอดการรีสตาร์ต (ไฟล์ JSON) |
| ทำไม | จำลอง `server.ts` / `queue.ts` ของ §264 ตรง ๆ — งานเดียวกับที่เจอ "บีบโค้ด" จึงเป็นงานเดียวที่ยืนยันซ้ำได้ว่า §264 แก้แล้วจริง |
| เปิดเผย | ทำจนจบไหม · เขียนเทสของตัวเองไหม · **longest line / บรรทัดต่อไฟล์** · ไฟล์แยกกี่ไฟล์ |
| เทสซ่อน | vitest ยิง server จริง ~12 เคส รวม concurrency limit, retry นับถูก, รีสตาร์ตแล้วงานยังอยู่ |

### งาน 2 — แก้บั๊กใน repo แปลกหน้า (Go)

| | |
|---|---|
| โจทย์ | repo Go สาธารณะขนาดกลาง (ไม่ใช่ Aetox — ห้ามได้เปรียบเรื่องรู้จักบ้าน) ที่ **ย้อน commit แก้บั๊กจริง**ออกไป เหลือเทสที่ commit นั้นเพิ่มไว้เป็นเทสซ่อน โจทย์คือข้อความ issue เขียนใหม่ด้วยคำของเรา |
| ทำไม | งานจริงส่วนใหญ่คือแก้ของที่ไม่ได้เขียนเอง — ต้องหา ต้องอ่าน ต้องแก้ให้น้อย |
| เปิดเผย | หาเจอไหม · แก้กี่ไฟล์เทียบกับ commit ต้นฉบับ · ทำเกินโจทย์ไหม · รันเทสที่มีอยู่ก่อนตอบ "เสร็จ" ไหม |
| เทสซ่อน | เทสจาก commit ต้นฉบับ + เทสเดิมทั้ง package ต้องยังเขียว |
| กติกาเลือก commit | แตะ ≤ 3 ไฟล์ · เพิ่ม/แก้เทสในตัว · บั๊กทำซ้ำได้ด้วยเทสนั้น · `go test` ผ่านออฟไลน์ (อุ่น module cache ก่อน) · ไม่ใช่ repo ที่โมเดลจำได้ทั้งก้อน (ไม่เอา stdlib, ไม่เอา top-100) |

### งาน 3 — แก้บั๊กใน repo แปลกหน้า (TypeScript)

เหมือนงาน 2 ทุกข้อ แต่เป็น TS/Node — เพื่อให้รูปร่างเดียวกันมีทั้งสองภาษา ถ้า harness ตัวไหน
เก่งภาษาเดียวจะเห็นตรงคู่นี้

### งาน 4 — รีแฟกเตอร์ใต้ข้อจำกัด (Go)

| | |
|---|---|
| โจทย์ | ไฟล์เดียวยาว ~1,000 บรรทัดใน repo สาธารณะ ให้แยกเป็นหลายไฟล์/แพ็กเกจย่อย โดย **API สาธารณะห้ามเปลี่ยน** · **ไม่มีไฟล์เกิน 400 บรรทัด** · เทสเดิมทั้งหมดต้องผ่าน · ห้ามแตะไฟล์นอกแพ็กเกจ |
| ทำไม | โจทย์ที่ "ทำจนจบ" กับ "ทำเกิน" อยู่ห่างกันแค่ก้าวเดียว — วัดวินัย ไม่ใช่ความสามารถ |
| เปิดเผย | เคารพขอบเขตไหม · ทำเกินโจทย์ (แก้ชื่อ ปรับ style เพิ่มฟีเจอร์) · โค้ดที่ได้ยังอ่านออกไหม |
| เทสซ่อน | เทสเดิม + สคริปต์เชิงกล: `go doc` ก่อน/หลังต้องเท่ากัน · `wc -l` ทุกไฟล์ ≤ 400 · `git diff --stat` นอกแพ็กเกจต้องว่าง |

### งาน 5 — โจทย์มีรู (ภาษาไหนก็ได้ · เล็ก)

| | |
|---|---|
| โจทย์ | เครื่องมือบรรทัดคำสั่งเล็ก ๆ ที่สเปกเว้นการตัดสินใจสำคัญไว้หนึ่งอย่างโดยตั้งใจ (เช่น "ตัดบรรทัดซ้ำ" — แยกตัวพิมพ์ใหญ่เล็กไหม รักษาลำดับไหม) |
| ทำไม | harness ที่ดีถามหรือบอกสมมติฐานก่อนทำ ไม่ใช่เดาเงียบ ๆ — **Aetox มีจุดอ่อนที่รู้อยู่ตรงนี้** (วางแผนไม่ค่อยถาม) งานนี้ใส่ไว้เพราะอาจแพ้ ตารางที่ Aetox ชนะทุกช่องไม่มีใครเชื่อ |
| เปิดเผย | ถาม / ประกาศสมมติฐาน / เดาเงียบ · ถามแล้วทำต่อจนจบไหม |
| เทสซ่อน | รับได้ทั้งสองความหมาย **ถ้าประกาศไว้** — เดาเงียบแล้วถูกได้ครึ่งคะแนน เดาเงียบแล้วผิดได้ศูนย์ |
| คำตอบสคริปต์ | ถ้า harness ถาม คนรันตอบด้วยข้อความเดียวที่เตรียมไว้ล่วงหน้า เหมือนกันทุกฝั่ง ตอบได้ครั้งเดียว |

**สิ่งที่ยังไม่ได้เลือก:** commit จริงของงาน 2 · 3 และไฟล์ของงาน 4 — ต้องเลือกตามกติกาข้างบน
แล้ว**จด hash ลงเอกสารนี้ก่อนรันรอบแรก** ห้ามเปลี่ยนโจทย์หลังเห็นผลรันแรก (ถ้าโจทย์พังจริง
ให้ทิ้งผลทั้งงานแล้วเริ่มงานนั้นใหม่ พร้อมจดว่าทำไม)

## 4. มาตรฐานคุณภาพ — สามชั้น ไม่มีฝั่ง

ไม่มี harness ตัวไหนเป็นมาตรฐาน — ถ้ามี ตารางจะวัดว่าใครเหมือนมัน ไม่ใช่ใครทำงานได้
มาตรฐานคือสิ่งที่เขียนไว้ก่อนรันและอ่านด้วยสคริปต์ เรียงจากเถียงไม่ได้ไปเถียงได้:

| ชั้น | วัดอะไร | อ่านโดย | น้ำหนัก |
|---|---|---|---|
| **1 · เทสซ่อน** | สัดส่วนเทสที่ผ่านต่อรัน (0–1) | สคริปต์ | **ตัวตัดสินหลัก** — ชั้นล่างพลิกผลชั้นนี้ไม่ได้ |
| **2 · เชิงกล** | build ผ่าน · lint ผ่าน (eslint / golangci-lint ตามภาษา) · longest line · บรรทัด/ไฟล์ · ไฟล์ที่แตะนอกขอบเขต · จำนวนรอบเรียกโมเดล · โทเค็นเข้า/ออก/cache · เวลาจริง | สคริปต์ | รายงานทุกตัว ไม่รวมเป็นคะแนน |
| **3 · LLM ตัดสิน** | อ่านง่าย · ชื่อ · ทำเกินโจทย์ · เทสที่เขียนเองมีความหมายไหม | โมเดล — ใต้กติกาข้างล่าง | เฉพาะที่ชั้น 1–2 วัดไม่ได้ · ถ้าชั้น 1 ต่างชัด ชั้นนี้เป็นแค่หมายเหตุ |

**กติกาของชั้น 3 (กันเข้าข้าง):** ผู้ตัดสิน**ไม่ใช่โมเดลในคู่นั้น** — คู่ DeepSeek ให้ Luna ตัดสิน
คู่ Luna ให้ DeepSeek ตัดสิน · ลบชื่อ harness และร่องรอย (ชื่อไฟล์ log, header) ออกจากทุกอย่างที่
ส่ง · สลับลำดับ A/B แบบสุ่มต่อครั้ง · ให้คะแนนแยกทีละเกณฑ์ 1–5 ห้ามถาม "อันไหนดีกว่า" ·
เก็บ prompt ผู้ตัดสินไว้ใน repo

**เจ้าของ** อ่านตัวอย่างสุ่ม 1 รันต่องานต่อ harness เพื่อเช็กว่าตัวเลขสามชั้นไม่โกหก — ไม่ใช่ให้
คะแนน เพราะเป็นเจ้าของ Aetox และคนอ่านตารางรู้

ต่อยอดจากกติกา 9 ข้อของ BENCHMARK.md §1 — ข้อ 1 (เครื่องเดียว รอบเดียว) และข้อ 8 (จดเวอร์ชัน)
ใช้ตรง ๆ ที่เพิ่มคือ:

| # | กติกา | ทำไม |
|---|---|---|
| H1 | **โมเดลเดียวกัน ระดับคิดเดียวกัน บัญชี/คีย์เดียวกัน** ทั้งสองฝั่งของคู่ | ตัวแปรเดียวคือ harness |
| H2 | workspace ใหม่ต่อรัน — copy จาก snapshot เดียวกัน ไม่ใช้ซ้ำ | รันก่อนหน้าทิ้งไฟล์ไว้ = ผลปน |
| H3 | prompt เดียวกันคำต่อคำ · **ยิงครั้งเดียว** ไม่มีข้อความตามหลัง (ยกเว้นงาน 5) | ข้อความที่สองคือคนช่วย ไม่ใช่ harness |
| H4 | ปิดสกิล · ทีม · sub-agent · MCP · เว็บ · ความจำข้ามเซสชัน ทุกฝั่ง | สภาพเปล่าเท่ากัน — Aetox ต้องปิดของตัวเองด้วย |
| H5 | โหมดอนุมัติ = เต็ม (full-access / yolo / `--yes`) ทุกฝั่ง | ไม่งั้นวัดว่าคนกดตอบเร็วแค่ไหน |
| H6 | เพดานเวลา 20 นาที/รัน · หมดเวลา = รันนั้นได้ 0 ในชั้น 1 และ**นับ** ไม่ทิ้ง | timeout คือผลอย่างหนึ่ง |
| H7 | 5 งาน × 3 รัน × 2 ฝั่ง ต่อคู่ · รายงาน**ทั้งสามค่า**และ median | 2 รอบของ §264 บอกทิศ 3 รอบเริ่มบอกขนาด |
| H8 | จดก่อนเริ่ม: เวอร์ชัน harness ทั้ง 5 · model id ที่ endpoint ตอบกลับ · commit hash ของโจทย์ · commit hash ของสคริปต์รัน | ตัวเลขไม่มีบริบทคือตัวเลขที่ทวนไม่ได้ |
| H9 | **ปิด auto-update** ของ Codex / OpenCode / Crush ตลอดชุด | เวอร์ชันเปลี่ยนกลางชุด = ชนข้อ 1 |
| H10 | เก็บ transcript + `git diff` ของทุกรันไว้ในโฟลเดอร์ผล | ให้คนอื่นอ่านซ้ำได้ และให้ชั้น 3 มีของอ่าน |

**ฝั่ง Aetox รันผ่านอะไร:** `aetox chat "โจทย์"` — ตั้งแต่ 14 ก.ย. 2026 (DECISIONS §268) CLI คือ
จอที่สามของเครื่องยนต์ตัวเดียวกับแอป นั่งที่โต๊ะโค้ดเสมอ โหลด `coding.md` ความจำ สกิล และ
เครื่องมือชุดเดียวกับหน้าต่าง คำตอบออก stdout งานที่ทำออก stderr คำถาม/การขออนุมัติอ่านจาก
stdin (ปิด stdin = ไม่ตอบ = ปฏิเสธ) ตั้ง `AETOX_DATA_ROOT` แยกให้การวัด จะได้ไม่ปน DB คีย์
และ "โปรเจกต์ล่าสุด" ของแอป — ก่อนหน้านั้น CLI เป็นลูปคนละตัวที่ไม่มีโต๊ะ วัดผ่านมันคือวัด
Aetox โดยไม่มี Aetox

## 6. ตัวเลขที่รายงาน และกฎการเผยแพร่

ตารางหลักหนึ่งตารางต่อคู่ แถว = งาน คอลัมน์ = ฝั่ง แต่ละช่อง = ชั้น 1 สามค่า + median
ตารางรองรวมชั้น 2 ทุกตัว ไม่มี "คะแนนรวม" — ตัวเลขเดียวที่รวมห้าอย่างคนละหน่วยคือตัวเลข
ที่ตั้งใจให้อ่านผิด (เหตุผลเดียวกับที่ BENCHMARK.md ไม่มี)

**ขึ้น BENCHMARK.md เป็น "ผล 6 — harness" ได้ต่อเมื่อ:** ครบ 120 รัน · ทุกรันในรอบเดียวกัน
(H8 ตรงกันหมด) · โจทย์ไม่ถูกแก้หลังรันแรก · โฟลเดอร์ผลอยู่ใน repo และ
[docs/PUBLISHED-NUMBERS.md](../PUBLISHED-NUMBERS.md) มีแถวชี้ไปที่คำสั่งรันซ้ำ
ก่อนหน้านั้นทุกตัวเลขอยู่ในไฟล์นี้ใต้ §9 เท่านั้น

ถ้า Aetox แพ้บางช่อง **ช่องนั้นขึ้นด้วย** — ตารางที่ชนะทุกช่องคือตารางที่ไม่มีใครเชื่อ และ
งาน 5 ถูกออกแบบให้เป็นช่องนั้นอยู่แล้ว

## 10. คำถามที่ยังเปิด

- **ระดับคิดฝั่ง DeepSeek:** Luna มี low ชัด แต่ DeepSeek ในสี่ harness แต่ละตัวเรียกระดับต่ำสุด
  ไม่เหมือนกัน ต้องเลือกตัวที่ทุกเจ้ามีจริง — ตัดสินตอนรันนำร่อง
- **งาน 5 ให้ Aider:** Aider ไม่มีกลไกถามกลับแบบ agent การ "ถาม" ของมันคือพิมพ์ในแชท —
  ต้องนิยามให้ชัดว่าอะไรนับเป็นถามก่อนรัน
- **หน้าต่าง Aetox ระหว่างรัน:** `aetox chat` ไม่มีหน้าต่าง ไม่มี browser/computer tools — เท่ากับคู่แข่งที่เป็น CLI แต่
  ต่างจากสภาพที่ผู้ทดสอบ §264 ใช้ (แอปเต็ม) ยอมรับได้เพราะ prompt และ tool set เดียวกัน แต่
  ต้องเขียนไว้
- **ต้นทุน:** ยังไม่ประเมิน — 90 จาก 120 รันอยู่บน DeepSeek (cache ~97%) น่าจะถูก ตัวเลขจริง
  มาจากรันนำร่อง
