# โมดูลจัดการโมเดล (ทิศทาง)

สถานะ 13 ก.ย. 2026: **คุยจบแล้ว ยังไม่ลงมือ** เจ้าของพักไว้ในวันเดียวกัน —
*"จู่ ๆ ก็ ขก รู้สึกไม่จำเป็นขนาดนั้นในตอนนี้"* เอกสารนี้จดสิ่งที่ตัดสินไปแล้วกับ
สิ่งที่วัดมาแล้ว เพื่อไม่ให้ต้องคิดซ้ำ ไม่ใช่สเปก

## 0. สองประโยค

**โมดูลนี้ตัดสิน ไม่ยิง** — มันตอบว่า "ใช้โมเดล X ตอนนี้ได้" แล้วคนเรียกเป็นคนยิง HTTP เอง

**และมันแนะนำ ไม่สลับเอง** — เจ้าของเคาะ 13 ก.ย.: *"ผมไม่ให้สลับโมเดลเองแต่จะมี
ข้อความบอกก่อน ผู้ใช้กดสลับได้เลย"*

ทุกข้อข้างล่างคือผลของสองประโยคนี้ ถ้าข้อไหนขัด ให้สองประโยคนี้ชนะ

## 1. ทำไมถึงมีเรื่องนี้

โผล่มาจากการคุยเรื่องทีมเอเจน (`agent-team-standard-2026-08-22.md`) ไม่ใช่จากปัญหาที่
ผู้ใช้เจอ เจ้าของ: *"ระบบทีมเอเจนใหญ่อ่ะควรจะมีกำกับดูแล"*

เหตุผลที่ทำก่อนทีมเอเจนคุ้มกว่าทำหลัง: **ทีมเอเจนคือตัวโหลดหนักตัวแรกจริง ๆ ของ
ระบบโมเดล** ถ้าปล่อยให้ทีมเอเจนไปเจอปัญหานี้เอง มันจะแก้ด้วยการแปะปะที่ทีม แล้ว
แชทธรรมดาจะไม่ได้อะไรเลย

## 2. ของที่มีอยู่แล้ว — สองชั้น และไม่ใช่สองชั้นที่คิดกันไว้

| ชั้น | ที่ไหน | ทำอะไร |
|---|---|---|
| บน | `internal/subagent/runner.go` | `maxConcurrent = 4` ลูกน้องพร้อมกันได้ 4 **ต่อหนึ่งเทิร์น** ตัวที่ 5 เข้าคิวรอ |
| ล่าง | `internal/model/httpclient.go` | โดน 429 แล้วค่อยอ่าน `Retry-After` → หลับ 1,2,4,8,16 วิ (เพดาน 16) |

ชั้นบนเป็นคำตัดสินของเจ้าของเอง 30 ส.ค. — *"เราต้องสร้างระบบแบบ รอโมเดลด้วย"* —
ตัวที่ 5 เดิมถูกตีกลับเป็นการ์ดแดง เปลี่ยนเป็นคิว

## 3. ช่องว่างจริงอยู่ตรงกลาง

**ชั้นบนนับผิดหน่วย** มันนับ "ต่อเทิร์น" ไม่ใช่ "ต่อผู้ให้บริการ" เปิด 3 แชทพร้อมกัน =
ยิงได้ 12 คำขอ ทั้งที่ผู้ให้บริการอาจรับได้ 5

**และมันไม่รู้จักปลายทาง** 4 ตัวยิง Ollama บนเครื่องตัวเอง (แรมหมด) กับ 4 ตัวยิง
OpenRouter (โดน 429) คนละเรื่องกัน แต่โค้ดปฏิบัติเหมือนกัน

**ชั้นล่างเป็นการตั้งรับ** รอชนกำแพงก่อนถึงเบรก ทีมเอเจน 20 ตัวจะชนพร้อมกันแล้ว
หลับพร้อมกัน

## 4. รูปที่เคาะ — หนึ่งประตู สี่คำตอบที่แยกกันได้

กับดักที่ต้องเลี่ยง: "โมดูลใหญ่จบทุกเรื่องโมเดล" คือวิธีเกิดของ god module
`internal/model` วันนี้มี 30 ไฟล์แล้ว (`quota.go` `balance.go` `pricefit.go`
`capabilities.go` `provider_catalog.go` `tool_support.go`) — **ของมันมีอยู่แล้วเยอะ
แค่จัดวางเป็น "คนขับรถ" ไม่ใช่ "หอบังคับการบิน"**

| ถาม | ตอบว่า | เปลี่ยนเพราะ |
|---|---|---|
| **เลือก** | คำขอนี้ควรไปโมเดลไหน | นโยบายผู้ใช้ / งานคนละชนิด |
| **ปล่อย** | ยิงตอนนี้ได้ไหม หรือรอ | โหลด / rate limit |
| **ล้ม** | ยิงแล้วพัง เอายังไงต่อ | ผู้ให้บริการล่ม |
| **นับ** | ใครใช้ไปเท่าไร | ต้องโชว์ผู้ใช้ |

สี่อันนี้เปลี่ยนด้วยเหตุผลคนละอย่าง ยัดรวมเป็นก้อนเดียว = แก้อันหนึ่งพังอีกสาม
แยกไว้แต่อยู่หลังประตูเดียว = control plane ที่แก้ทีละชิ้นได้

**กฎเหล็กข้อเดียวที่กันมันบวม: โมดูลนี้ตัดสิน ไม่ยิง** ถ้าให้มันยิงเอง ทุกอย่าง —
streaming, thinking, tool call, รูป, SSE — ต้องเดินผ่านมัน แล้วมันจะกลายเป็นทั้งแอป
ภายในเดือนเดียว

## 5. ข้อจำกัดของเจ้าของ และมันเปลี่ยนสถาปัตยกรรมทั้งหมด

เจ้าของเคาะ 13 ก.ย. สองข้อ:

1. **ไม่สลับเอง** — แจ้งว่าควรสลับไปตัวไหน ผู้ใช้กดเอง
2. **เปิดใช้แค่ตอนผู้ใช้ตั้งค่าไว้** — อาจมีหน้าตั้งค่าใหม่ของตัวเอง

**ข้อ 1 คือสิ่งที่ทำให้งานนี้เบา** ถ้าสลับเอง โมดูลต้องนั่ง *บน* ทางเดินของทุกคำขอ
(แบบ 9Router) → แตะ `cognitive/agent.go` translator streaming ทั้งหมด
แต่ "บอกก่อน ผู้ใช้กด" ทำให้มันนั่ง *ข้าง* ทางเดิน — เป็นตัวอ่านกับตัวแนะนำ ไม่ใช่ประตู

**และมันปิดปัญหา prompt cache ไปด้วย** cache ผูกกับโมเดล การสลับกลางบทสนทนา
ทิ้ง cache ทั้งก้อน — สลับไปตัวถูกกว่าอาจแพงขึ้นเพราะต้องส่ง context ใหม่ทั้งหมด
ผู้ใช้กดสลับ *หลังเทิร์นล้มไปแล้ว* = สลับที่ขอบของงาน ซึ่งไม่มี cache ให้ทิ้งอยู่แล้ว

กฎที่ตามมาและควรถือไว้แม้จะเปลี่ยนใจภายหลัง: **สลับที่ขอบของงาน ไม่สลับกลางงาน**

## 6. หลักฐานจากเจ้าอื่น — 9Router

https://github.com/decolua/9router — gateway ท้องถิ่น (Next.js พอร์ต 20128) เปิด
endpoint เดียวแบบ OpenAI-compatible route ไป 40+ providers แปลฟอร์แมตโดย pivot
ผ่าน OpenAI format state เก็บ SQLite ที่ `~/.9router`

**สามกลไกที่เกี่ยวกับเรา**

1. **Combo** = fallback chain ที่ผู้ใช้ตั้งเอง ตั้งชื่อ + ใส่รายการโมเดลเรียงลำดับ
   แล้วเรียกด้วยชื่อ combo แทนชื่อโมเดล
2. **3 ชั้นเป็นค่าเริ่มต้น** — Subscription → Cheap → Free
3. **ตัวตัดสินว่าเมื่อไรควรสลับ** — `open-sse/services/accountFallback.js` +
   `open-sse/config/errorConfig.js` รวมกันประมาณ 80 บรรทัด และนั่นคือทั้งหมด

**`ERROR_RULES` ไล่จากบนลงล่าง กฎข้อความก่อน แล้วค่อยกฎ status**

| เจอ | ทำ |
|---|---|
| ข้อความมี `rate limit` / `too many requests` / `quota exceeded` / `capacity` / `overloaded` | backoff แล้วสลับ |
| ข้อความมี `no credentials` | พัก 2 นาที |
| status 401 / 402 / 403 / 404 | พัก 2 นาที |
| status 429 | backoff แล้วสลับ |
| **อะไรก็ตามที่ไม่เข้าข้อไหนเลย** | **พัก 30 วิ แล้วสลับอยู่ดี** |

backoff: เริ่ม 2 วิ คูณสอง เพดาน 5 นาที 15 ระดับ

**สามรายละเอียดที่ควรลอก**

- **`shouldFallback: true` เป็นค่าตั้งต้น** error ที่ไม่รู้จักก็ยังสลับ — fail-forward
  ไม่ใช่ fail-fast ปรัชญาคือ "ผู้ใช้ต้องได้คำตอบ" ไม่ใช่ "ระบบต้องถูกต้อง"
- **cooldown ผูกกับบัญชี ไม่ใช่โมเดล** เก็บเป็น `unavailableUntil` / `rateLimitedUntil`
  เป็น ISO timestamp ต่อบัญชี ทำให้ถามได้ว่า "ตัวไหนว่างเร็วสุด"
  (`getEarliestRateLimitedUntil`)
- **`MAX_RATE_LIMIT_COOLDOWN_MS = 30 นาที`** คอมเมนต์ในโค้ดบอกเหตุผลตรง ๆ ว่า
  *"codex resets_at can be 5-6h"* — **ไม่เชื่อเวลาที่ผู้ให้บริการบอกมาแบบดิบ ๆ**
  เพราะรอ 6 ชั่วโมงคือตายไปแล้ว ตัดเพดานไว้ 30 นาทีแล้วลองใหม่

**ลำดับ fallback ซ้อนสองชั้น** บัญชีอื่นของ provider เดิมก่อน → หมดแล้วค่อยขยับไป
โมเดลถัดไปใน combo

**สามอย่างที่เขาไม่มี และเป็นช่องที่เราทำได้ดีกว่า**

- **prompt cache** เขาไม่คิดเรื่องนี้เลย (ดู §5)
- **คิวมีลำดับความสำคัญ** เขาเป็น proxy ไม่รู้ว่าคำขอไหนคือคนพิมพ์อยู่ ไหนคือ
  ลูกน้องทีมเอเจน **เรารู้** — ไม่มีอันนี้ ทีมเอเจน 20 ตัวจะทำให้แชทที่ผู้ใช้กำลัง
  พิมพ์ค้าง แล้วผู้ใช้จะโทษว่าแอปพัง
- **เลือกตามความสามารถ** เขาสลับตามโควตาอย่างเดียว เรามี `ModelCapabilities`
  (tools/input/output/thinking) อยู่แล้ว — สลับไปตัวที่เรียกเครื่องมือไม่ได้ = งานพังเงียบ

**ข้อสังเกต** เขาออกแบบรอบ "หลายบัญชีต่อ provider" ส่วนเราเป็นหนึ่งคีย์ต่อหนึ่งแถว
แต่ §245 (11 ก.ย.) เพิ่งเปิดให้ผู้ใช้เพิ่มแถวเองได้เป็นลิสต์แล้ว โครงเขาจึงยกมาใช้ได้ตรง ๆ

### รื้อ: ไม่มี

- `SwitchModel` / `SwitchProvider` ใน `desktop/app.go` **มีอยู่แล้วครบ** ปุ่มใหม่แค่
  เรียกของเดิม
- `maxConcurrent` และคิวลูกน้อง — ไม่แตะ
- backoff 429 ที่มีอยู่ — ไม่แตะ เป็นตาข่ายชั้นล่างเหมือนเดิม
- **จุดที่ 6 มีแบบแผนในรีโปอยู่แล้ว** `internal/callfault` กับ `internal/statereport`
  คือแพ็กเกจ "ติดป้ายชนิดของ error" ที่วางเป็น leaf package พอดี ทำตามรูปเดิมได้เลย

### สามอย่างที่ข้อจำกัดของเจ้าของตัดทิ้งไปฟรี ๆ

| ของที่ 9Router ต้องมี | เราไม่ต้อง เพราะ |
|---|---|
| translator แปลฟอร์แมตข้าม provider | เราไม่ได้เป็น gateway มี provider client อยู่แล้ว |
| สลับกลางสตรีม (ยากที่สุด) | ผู้ใช้กดหลังเทิร์นจบ |
| จัดการ prompt cache ตอนสลับ | สลับที่ขอบเทิร์นเสมอ |

## 8. จุดเสี่ยงสองข้อ

**จุดที่ 6 แอบใหญ่กว่าที่เห็น** วันนี้ `httpclient.go` ตัดสินใจถูกอยู่แล้ว แต่ผลลัพธ์
ออกมาเป็นประโยคภาษาคน ไม่ใช่ชนิดข้อมูล งานคือ *เพิ่มป้าย ไม่แก้การตัดสิน* —
เผลอไปแก้การตัดสินด้วยจะพ่วง §243 (500 ไม่ใช่บิล) ที่เพิ่งแก้ไป 11 ก.ย. เข้ามา

**"เปิดใช้แค่ตอนตั้งค่าไว้" ต้องแปลว่าปิดสนิท** ถ้าสวิตช์ปิดแล้วยังมีโค้ดวิ่งอ่าน quota
อยู่เบื้องหลัง คนที่ไม่ได้เปิดจะจ่ายค่าฟีเจอร์ที่ไม่ได้ใช้ เขียนเป็นกฎไว้:
**ปิด = ไม่มีการเรียกใด ๆ เกิดขึ้น** และมีเทสต์บังคับ

## 9. ยังค้าง

1. **ชื่อของสิ่งนี้** COMPANY.md §8 บังคับหนึ่งความหมายหนึ่งคำ และคำว่า "โมเดล"
   มีความหมายอยู่แล้ว
2. **ตารางจำแนก error ของเรา** จะลอก `ERROR_RULES` มาทั้งชุดหรือตัด
3. **หน้าตั้งค่าหน้าตายังไง** และมันเป็นห้องใหม่หรือหมวดใหม่ในหน้าตั้งค่าเดิม
4. **คิวลำดับความสำคัญ** (คนพิมพ์ > ลูกน้อง) คุยแล้วว่าสำคัญที่สุดในสามข้อของ §6
   แต่ยังไม่ออกแบบ และมันคือชิ้น "ปล่อย" ใน §4
5. **โควตาปรับตัวเอง** (หด/ขยายแบบ AIMD) เสนอไปแล้ว ยังไม่เคาะ — และถ้า
   ไม่สลับเองแล้ว อาจไม่จำเป็นเลย
6. **เพดานงบ** 9Router มี (รายวัน/รายเดือน แล้วตกไปชั้นฟรี) เรายังไม่ตัดสิน
