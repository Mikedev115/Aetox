# ปล่อยรุ่น Aetox

**ลำดับที่เป็นความจริงอยู่ที่ [docs/RELEASING.md](../../../docs/RELEASING.md)** — อ่านมันทุกครั้ง
ไฟล์นี้ไม่คัดขั้นตอนพวกนั้นมาเขียนซ้ำ (ที่สองที่ตอบคำถามเดียวกันคือหนี้) สิ่งที่อยู่ในนี้คือ
ส่วนที่ RELEASING.md ไม่ได้ตอบ: **จะแปลงกองงานที่ค้างอยู่ในทรี ให้เป็นประวัติที่อ่านรู้เรื่อง
และเป็นบันทึกรุ่นที่ไม่โกหก ได้ยังไง**

## กติกาประจำ

- **ไม่ต้องรัน verify.sh ไม่ต้องรันสวีตเทสต์** เจ้าของเทสต์มาก่อนสั่งเสมอ และมันช้า
  ข้อยกเว้นเดียวคือ `go test ./internal/version/` (< 1 วินาที) ซึ่งเป็นด่านที่คุมไฟล์
  ที่ *คุณเพิ่งแก้เอง* — เจ้าของไม่ได้เทสต์ส่วนนั้น
- **อย่าคอมมิตของที่ไม่ใช่โค้ด** ทรีของเจ้าของมีไฟล์ค้างเป็นสิบเสมอ: worktree ซ้อน
  (`aetox-head2/`), `.aetox-attachments/`, ร่างเอกสารที่ยังคิดไม่จบ, ไฟล์สแครช
  คอมมิตเฉพาะ tracked ที่ถูกแก้ + ไฟล์เทสต์ใหม่ ที่เหลือรายงานเป็นบรรทัดเดียวว่าเว้นไว้เพราะอะไร
- **ห้าม `git checkout` ทั้งไฟล์ ห้าม stash** งานที่ยังไม่คอมมิตของเขาหายไม่ได้
  การแยกฮังก์ทำที่ **index** เท่านั้น (`git apply --cached`) ซึ่งไม่แตะทรีเลย

## 1. อ่านของที่ค้าง แล้วแยกเป็นเรื่อง

`git status --short` · `git diff --stat` · แล้วอ่าน diff จริงให้ครบ **โค้ดของโปรเจกต์นี้
อธิบายตัวเองในคอมเมนต์** เรื่องเล่า เหตุผล และประโยคที่เจ้าของพูดวันนั้น มักอยู่ในคอมเมนต์
เหนือฟังก์ชันที่เปลี่ยน — นั่นคือวัตถุดิบของทั้ง commit message และบันทึกรุ่น ไม่ต้องเดาเอง

จัดกลุ่มเป็น **หนึ่งคอมมิต = หนึ่งเรื่อง** เหมือนที่ `git log` เล่มนี้ทำมาตลอด
ไฟล์ใหญ่อย่าง `Chat.svelte` / `cockpit.svelte.ts` มักคร่อมสามสี่เรื่องพร้อมกัน ให้แยกฮังก์:

```bash
# เอาเฉพาะฮังก์ที่ 2 6 7 ของไฟล์นี้เข้า index
git diff --no-color -- <file> | awk -v want=" 2 6 7 " '
  BEGIN{n=0;inh=0}
  /^@@/{n++;inh=(index(want," " n " ")>0); if(inh)print; next}
  {if(!inh){if(/^(diff |index |--- |\+\+\+ )/)print}else print}' > /tmp/p.patch
git apply --cached --recount /tmp/p.patch
```

ฮังก์ที่คร่อมสองเรื่อง **และเป็นการเพิ่มบรรทัดล้วน** ให้ลบบรรทัด `+` ของอีกเรื่องออกจากแพตช์
(`sed '/^+.*เริ่ม/,/^+.*จบ/d'`) แล้วคอมมิตเรื่องแรก — ส่วนที่เหลือจะโผล่เป็น diff ธรรมดาเอง
ในรอบถัดไป

**เช็คว่า HEAD คอมไพล์ได้ไหมก่อนเรียงลำดับ** เคยเกิดแล้ว: คอมมิตก่อนหน้าพา `app.go`
ที่เรียกฟังก์ชันซิกเนเจอร์ใหม่ขึ้นไป แต่ตัวฟังก์ชันยังค้างในทรี ถ้าเจอแบบนี้
ให้คอมมิตเรื่องที่ปิดรอยนั้น **เป็นอันแรก** และเขียนบอกไว้ในข้อความคอมมิต

## 2. ข้อความคอมมิต

ภาษาไทย · `fix(ขอบเขต):` หรือ `feat(ขอบเขต):` · **หัวเรื่องบอกอาการ ไม่ใช่บอกวิธีแก้**

> `fix(เอเจน): หน้ารายชื่อบอกว่าเอเจนไม่มีความจำ ทั้งที่ตอนคุยจริงมันมี`

ตัวเรื่อง: อาการที่วัดได้ (ตัวเลขจริงจากแอปที่รันอยู่ ถ้ามีในคอมเมนต์) → ทำไมมันเกิด →
ตัดสินใจอะไร และ **อะไรที่จงใจไม่ทำ** ปิดท้ายด้วย
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`

## 3. กวาดเอกสารที่เพิ่งกลายเป็นเท็จ

ทำ **ก่อน** บั๊มป์เวอร์ชัน ไล่หาประโยคเก่าที่การเปลี่ยนแปลงรอบนี้ทำให้ผิด:

- `docs/DECISIONS.md` — เพิ่ม `## <n>. Decision — <ชื่อ> (YYYY-MM-DD)` ต่อท้าย
  (ไม่มีเส้น `---` คั่นในช่วงท้ายเล่ม) และประโยคเก่าที่ผิดแล้วให้ **ขีดฆ่า `~~…~~`
  พร้อมชี้ไป §ใหม่ ไม่ใช่ลบ** — บันทึกที่ถูกลบคือบันทึกที่คนอ่านคราวหน้าไม่รู้ว่าเคยเชื่ออะไร
- `internal/skill/skills/aetox/SKILL.md` — สกิลนี้ต้องจริงตามระบบเสมอ grep หาคำที่
  เกี่ยวกับสิ่งที่เพิ่งเปลี่ยน
- `README.md` / `README.th.md` — สามข้อใต้หัวข้อสถานะเปลี่ยนเป็นของรุ่นนี้
  README บอกว่าแอป **เป็น** อะไร ห้ามใส่ของที่ยังไม่ปล่อย
- แลนดิ้งเพจอยู่รีโปแยก [aetox-landing](https://github.com/Mikedev115/aetox-landing) — ป้ายเวอร์ชัน
  อ่านจาก Releases เอง ไม่ต้องแก้ · ถ้าตัวเลข/ข้อความบนหน้าเว็บกลายเป็นเท็จ ไปแก้ที่ `lib/i18n/` ของรีโปนั้น
  แล้วสั่ง `gh api repos/Mikedev115/aetox-landing/dispatches -f event_type=aetox-release` ให้ build ใหม่
- ห้าม em dash ในสตริงที่ขึ้นบนหน้าจอแอป

## 4. บั๊มป์ · แท็ก · ปล่อย

ตามลำดับใน [RELEASING.md](../../../docs/RELEASING.md) ทั้งหมด ย่อไว้ให้ไม่ลืม:
บั๊มป์ `internal/version/version.go` ก่อนที่เดียว → `go test ./internal/version/`
บอกเองว่าไฟล์ไหนยังไม่ตรง → เขียน `docs/release-notes/v<ver>.md` → คอมมิต →
`git push origin main` **ก่อน** แล้วค่อย `git tag -a v<ver>` + push tag →
`gh run watch <id> --exit-status` → `gh release edit v<ver> --draft=false --latest` →
`gh run download <id> -n msix-store-package -D ~/Downloads` → เติม scoop hash

**สามข้อที่ลืมแล้วเจ็บ:** งานบิ้วเขียวไม่เท่ากับปล่อยแล้ว (มันเป็น draft เสมอ) ·
`.msix` ต้องอัป Partner Center ด้วยมือ ซึ่งเป็นการเผยแพร่ในชื่อเจ้าของ **จึงหยุดที่
วางไฟล์ไว้ในโฟลเดอร์ดาวน์โหลดแล้วบอกเขา ไม่ใช่กดส่งเอง** · scoop hash มาจากรุ่นที่
ปล่อยจริงเท่านั้น ไม่ใช่จากไฟล์ที่บิ้วในเครื่อง

## 5. บันทึกรุ่น (`docs/release-notes/v<ver>.md`)

ภาษาไทย ขึ้นต้น `# 🧩 Aetox v<ver>` แล้วสองสามบรรทัดว่ารุ่นนี้เป็นรุ่นของอะไร
เรียงหัวข้อจากเรื่องใหญ่ลงเล็ก แต่ละหัวข้อเดินคู่ **เรื่องเดิม → รุ่นนี้**

- เขียนจากอาการที่ผู้ใช้เจอ ไม่ใช่จากชื่อฟังก์ชันที่แก้
- ตัวเลขที่ใส่ต้องมีที่มาจริง (คอมเมนต์ในโค้ด หรือ commit body) **ห้ามแต่งตัวเลขเทสต์
  หรือเคลมว่าสวีตเขียว ถ้าไม่ได้รัน** — เขียนว่า "เทสต์ที่เพิ่มในรุ่นนี้" แล้วไล่ชื่อแทน
- ของที่จงใจไม่ทำ เขียนไว้ด้วย มันคือครึ่งหนึ่งของการตัดสินใจ
- ปิดท้ายหัวข้อรวม "อื่น ๆ ในรุ่นนี้" สำหรับคอมมิตย่อย
- อ้างอิงสไตล์: `docs/release-notes/v1.5.15.md` และ `v1.5.16.md`

## 6. รายงานกลับ

บอกเป็นข้อ: คอมมิตอะไรบ้าง · เอกสารไหนถูกกวาด · ลิงก์ release · ไฟล์ `.msix` อยู่ที่ไหน
และ **ค้างอะไรไว้ให้เจ้าของทำต่อ** (อัป Partner Center, เติม scoop hash, ไฟล์ที่ไม่ได้คอมมิต)
